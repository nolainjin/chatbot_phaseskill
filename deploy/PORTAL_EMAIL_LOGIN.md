# 이메일 코드 로그인 · 사전 등록 및 가입 신청

2026-11-04. 사용자 지시에 따라 **Gmail만 허용하는 비밀번호 없는 이메일 링크 로그인**을 공개 반영했다.
숫자 코드 로그인도 구현되어 있지만 현재 무료 기본 메일에서는 활성화하지 않는다.
이전 [비밀번호+PKCE 공개 시험](PORTAL_CLOUD.md)의 같은 Vercel/Supabase 프로젝트와 상담 자료를 사용한다.

## 현재 공개 방식과 제한

- 로그인에는 이메일 한 칸과 `이메일 로그인 링크 받기`, `회원가입/신청`만 표시한다.
- `PORTAL_EMAIL_LOGIN=1`, `PORTAL_EMAIL_DELIVERY=link`, `PORTAL_EMAIL_DOMAINS=gmail.com`을 사용한다.
- 기본 SMTP의 조직 팀원 제한 때문에 `PORTAL_EMAIL_SEND_ALLOWLIST`에는 승인된 Owner Gmail 한 주소만 둔다.
  다른 Gmail로 신청하고 관리자가 기관/역할을 지정할 수 있지만, SMTP 연결 전에는 인증 메일을 발송하지 않는다.
  Gmail 도메인 허용이 모든 Gmail 주소로의 발송 가능을 뜻하지 않는다. 화면과 신청/승인 응답에도 제한을 표시한다.
- 새 프로젝트, 새 발신 계정, 유료 플랜, SMTP 자격증명은 만들거나 선택하지 않았다.
- 이메일 링크도 같은 브라우저에서 10분 내 한 번만 사용한다. callback에서 query를 즉시 지우고,
  Strict 쿠키의 시도/nonce 및 CSRF와 state·PKCE를 함께 확인한 뒤 자동으로 포털에 진입한다.
  메일 링크를 누른 뒤 별도의 확인 버튼은 필요하지 않다. 실패 때만 재시도 버튼을 표시한다.
  최초 HTTP URL이 호스팅/인증 제공자 로그에 전혀 남지 않는다고 보장하지 않는다.
- 이메일 로그인 성공 시 세션·브라우저 nonce 쿠키·기기 레코드는 최대 14일 유지한다.
  `PORTAL_EMAIL_SESSION_SECONDS` 기본값은 1209600이며 이를 초과하는 설정은 거부한다.
  같은 브라우저에서 재접속하면 이메일 입력·메일 발송 없이 진입한다. 활동해도 만료 시각은 늘어나지 않는다.
  30분 유휴 만료는 이메일 모드에 적용하지 않는다. 최초/다른 브라우저, 쿠키 삭제, 명시적 로그아웃,
  14일 만료 후에는 이메일 인증을 다시 받아야 한다. IP 변경만으로 다시 인증하지 않는다.
  기기 해제·계정 정지·인증 버전 변경은 기간이 남아 있어도 차단하고, 기관·등록 관리자 권한도 요청마다 재확인한다.
  기존 8시간 세션은 소급 연장하지 않으며 새 이메일 로그인부터 적용한다.
- 숫자 코드와 링크 검증 API는 서버 설정으로 상호 차단한다. 시도에도 `link-v1:` 모드를 저장해
  배포 설정 변경 전의 pending을 다른 검증 방식으로 해석하지 않는다. 기존 숫자 코드 구현은 아래에 기록한다.
- migration006은 schema-only 비공개 백업 후 트랜잭션으로 적용하고, 기존 Owner만 등록 관리자로 지정한다.
  기존 기관/접수/보고서를 이관하거나 다시 생성하지 않는다.
- 최종 배포/실메일 결과는 별도 공개 시험 증거에 기록한다. 로컬 검사만으로 실제 수신을 주장하지 않는다.

## 숫자 코드 후보의 사용 흐름 (현재 공개는 위의 링크 방식)

- 로그인 첫 화면: 이메일 한 칸, `인증번호 받기`, `회원가입/신청`.
- 미리 등록된 이메일: 메일 코드 확인 → 지정된 기관과 역할로 로그인.
- 가입 신청: 이메일만 저장하고 승인 대기. 계정·기관 권한·Auth 사용자를 자동 생성하지 않는다.
- 이메일 등록 관리자: 기존 계정의 `is_registrar`를 별도로 부여한다. 관리자만 신청 목록을 보고,
  이메일·기관·요약/상담사/기관관리자 역할을 지정해 사전 등록 또는 승인한다.
  기관의 `member:manage`만 가진 담당자는 이 전역 등록 권한을 받지 않는다.
- 새 이메일의 첫 코드 확인에서만 Supabase 사용자 UUID를 연결한다. 확정 이메일·기존 UUID가 다르면 거절한다.
- 새 세션을 시작할 때 이메일 인증이 필요하다. 인증한 브라우저의 세션이 유효하면 바로 진입한다.
  이메일 세션은 위의 고정된 최대 14일 정책을 따르며, 로그인 유지 중 IP 변경은 재인증 사유가 아니다.
- `/portal`, `/portal/`, `/portal/index.html`, `/portal/login`은 같은 동적 화면이다.

## 보안 경계

인증 시도는 HttpOnly·SameSite=Strict 쿠키 두 개, CSRF, 10분 만료, 5회 오입력 제한과 일회용 상태에 결합한다.
클라우드에서는 Secure 쿠키를 쓴다. 성공 직전에 사용자 활성·인증 버전·활성 기관 소속을 재확인한다.
공급자 세션은 브라우저에 주거나 저장하지 않고 즉시 폐기한다.
새 이메일 모드에서는 이전 비밀번호 로그인·기기 인증·PKCE 교환 API가 닫힌다.

미등록 주소와 등록 주소의 공개 응답 문구·상태·쿠키 형식은 같다. 다만 등록된 주소에만
공급자 발송을 동기 호출하므로 응답시간 차이가 남는다. 등록 여부의 완전한 은닉을 보장하지 않는다.
운영에서 시간차까지 줄이려면 신뢰 가능한 발송 큐를 별도로 연결해야 한다.
신청자의 이메일 소유는 신청 순간이 아닌 코드 로그인 시 확인하며, 관리 화면에도 이를 알린다.

재발송은 기본 60초, 주소별 최대 시간당 2회다. 공급자 실패도 발송 예산을 환불하지 않는다.
프로젝트 발송 예산 `PORTAL_PROVIDER_EMAILS_PER_HOUR`의 기본값은 2다.
별도 SMTP 연결 뒤 실제 공급자·Supabase 제한에 맞게 이 값과 Auth rate limit을 함께 결정한다.
만료 인증 시도는 하루, 미승인/거절 신청은 30일 뒤 정리 대상이다.

## 나중에 숫자 코드와 다른 담당자 발송을 활성화할 때

현재 Supabase 무료 기본 메일은 조직 팀원에게 시간당 2통만 보낸다.
대시보드에서 확인한 기본 템플릿은 링크 형식이고, 제목/본문 수정은 custom SMTP 또는 Pro가 필요하다.
요금제·발신 계정은 임의로 바꾸지 않았다.

1. 사용자가 발신 계정을 선택한다. 기존 Gmail로 소규모 시험 또는 별도 발신용 Gmail이 가능하다.
   Gmail SMTP는 Google 2단계 인증과 사용 가능한 앱 비밀번호가 필요하다. 비밀은 채팅/Git에 넣지 않는다.
2. 기존 프로젝트의 custom SMTP 설정을 완료하고 실제 발송을 확인한다.
3. `Magic link or OTP` 및 신규 사용자용 `Confirm sign up` 템플릿에 숫자 `{{ .Token }}`을 넣는다.
   단순히 링크를 코드 입력 화면으로 바꾸는 것만으로는 완료되지 않는다.
4. 검토된 additive migration과 기존 Owner의 등록 관리자 권한을 적용한다.

   ```sh
   .venv/bin/python scripts/portal_email_upgrade.py cloud --registrar OWNER_EMAIL
   ```

   이 스크립트는 고정된 기존 DB만 허용하며 schema-only 비공개 백업, 트랜잭션 및 checksum을 사용한다.
   계정·상담 자료를 새로 만들거나 이관하지 않는다. 운영용 신규 Auth 사용자는 승인된 이메일의
   첫 OTP 요청에서만 만들어지며, 메일 소유 확인 전에는 앱 세션이 생기지 않는다.
5. 동일 Vercel 프로젝트에 `PORTAL_EMAIL_LOGIN=1`을 등록하고 검증한 커밋을 배포한다.
6. 기존 사용자와 새로 사전 등록한 별도 시험 사용자의 실제 숫자 코드 수신·첫 UUID 연결,
   교차 기관 차단, 코드 재사용/만료, 로그아웃·재로그인과 재배포 지속성을 확인한다.

위 순서를 마치기 전에는 공개 서비스의 숫자 코드 모드를 켜지 않는다. 현재 공개 시험은 위의 링크 모드와 Owner 수신 제한을 사용한다.
