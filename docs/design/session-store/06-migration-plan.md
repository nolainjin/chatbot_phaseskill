## 0. 이 문서가 정하는 것 — 한 문장

이행은 **세 축(37 + 9 + 10)을 여덟 단계로 나눈 것**이고, 각 단계는 그 단계만으로
`209 passed` 를 통과해야 하며, **통과하지 못한 단계는 다음 단계로 넘어가지 않고 그 자리에서
되돌린다.**

이 한 문장이 Phase 5 의 전제 T3(§13.1)와 T4(§13.2)를 갚는 방식이다. T3 은 "전건 이행"을
요구하고, 단계 분할은 그 전건을 **잊을 수 없는 형태**(§11 의 라인 단위 대조표)로 만든다.

## 1. 이행 대상의 실측 총량

### 1.1 세 축

| 축 | 대상 | 총량 | 근거 | 받는 단계 |
|----|------|------|------|-----------|
| **A** | `_sessions` **외부** 직접 접근 | **37곳 / 13파일** | [01 §2](./01-current-state.md) | S3(1) · S4(4) · S5(32) |
| **B** | `storage.append_turn` 호출 | **9곳** (전부 `app/chat.py`) | [01 §5.1](./01-current-state.md) | S7(9) |
| **C** | 소유자·진입점 | **10곳** | `app/chat.py` 내부 6 + `app/main.py` 3줄 + `app/chat.py:353` | S2(10) |

A·B 두 축이 Phase 5 의 전제 **T3** 그 자체다([05 §8.2](./05-invariants.md)). C 축은 37 에
포함되지 않지만(`app/chat.py` 가 `_sessions` 를 **소유**하는 모듈이라 Phase 1 이 별도 행에
뒀다), C 를 이행하지 않으면 A 를 이행할 대상 자체가 없다 — 순서상 가장 먼저다.

### 1.2 산술 검산

```
A축 37 = lifecycle 7 (.pop() / .clear())
        + 첨자 읽기 30 (.slots 19 + .history 1 + 변수 대입 10)

S3 1  = app/knowledge_pack_exercise.py                    (lifecycle 1)
S4 4  = scripts/ 3파일                                     (lifecycle 4)
S5 32 = tests/ 9파일 = 첨자 읽기 30 + lifecycle 2
                                                    합계 = 37   ← 누락 0건 (§11)
```

### 1.3 스펙 표기 하나를 여기서 정정한다 — "S5 = 30" vs "S5 = 32"

phase 스펙의 S5 항목은 표제를 "테스트 첨자 읽기 **30곳**"으로 쓰면서 파일별 열거에
`tests/test_math_pack.py 2` 를 포함해 합이 **32** 가 된다. 두 수는 모순이 아니라 **서로 다른
것을 센다.**

- **30** 은 성격별 집계다 — 첨자 읽기만 센다. `tests/test_math_pack.py:29`·`:72` 는
  `.pop(...)` 이라 **lifecycle** 이고 30 에 들어가지 않는다([01 §2.2](./01-current-state.md)가
  이미 그 두 줄을 lifecycle 표에 뒀다).
- **32** 는 단계 배정 집계다 — S5 는 "테스트 디렉터리"라는 파일 경계로 묶이므로 그 2곳도
  받는다. S3(app/)·S4(scripts/) 어느 쪽도 `tests/` 를 받지 않기 때문이다.

따라서 **S5 = 첨자 읽기 30 + lifecycle 2 = 32곳**이고, "첨자 읽기 30곳의 파일 단위 재분할"은
S5-a~S5-f·S5-h·S5-i 여덟 하위 단계가 담당하며, S5-g 가 lifecycle 2곳을 따로 받는다(§7).
이렇게 나누지 않으면 §11 의 대조표에서 두 줄이 **어느 성격에도 속하지 않은 채 사라진다.**

## 3. S1 — 스토어 계층 신설

### 3.1 산출물

[04 §1.5](./04-interface.md)의 연산 11개와 [04 §7.2~7.5](./04-interface.md)의 스키마를 구현하는
신규 모듈 1개. 이 단계에서는 **아무도 그 모듈을 호출하지 않는다** — 기존 경로는 그대로
`_sessions` dict 를 쓴다. 그래서 S1 의 배포 영향이 0 이고, 실패해도 신규 파일만 지우면 된다.

### 3.2 스키마 부트스트랩의 소유자와 시점 ★

**"누가 DB 를 만드는가"에 답이 없으면 D01 이 약속한 비개발자 클론-후-실행 보증이 빈다.**
오늘 그 보증을 지탱하는 경로는 `시작하기-맥.command:12` → `run.py` → `run.py:267`
(`subprocess.run(argv, cwd=str(REPO_ROOT), ...)`)이고, 배포 경로는 `Dockerfile:30` 의 `CMD` 가
uvicorn 을 **직접** 부른다. 두 경로가 공유하는 유일한 지점은 `app.main:app` 이다.

#### 소유자 — 후보와 채택

| 후보 | 동작 | 판정 |
|------|------|------|
| `run.py` 의 환경 점검·복구 단계 | 기동 전에 DB 를 만든다 | **기각.** Docker 경로가 `run.py` 를 거치지 않는다(`Dockerfile:30` 이 uvicorn 을 직접 부른다). 배포에서만 DB 가 없는 상태가 되고, 그 실패는 첫 요청에서야 드러난다 |
| 별도 마이그레이션 스크립트를 운영자가 수동 실행 | `scripts/` 에 두고 안내한다 | **기각.** "클론 후 바로 실행"이 깨진다 — 비개발자에게 실행 순서를 요구하는 순간 D01 의 판단 기준을 위반한다 |
| **스토어 모듈 자신 — 채택** | 연결을 얻는 경로가 **그 프로세스에서 처음 열릴 때** 부트스트랩을 1회 수행한다 | **채택.** 진입점 중립이다. 서버(두 경로)·배치·`scripts/`·테스트가 전부 같은 규약을 얻는다 |

> **소유자 = 스토어 모듈의 연결 획득 경로. 시점 = 그 프로세스가 그 DB 파일을 처음 열 때 1회.**
> `app/main.py` 의 애플리케이션 기동 훅이 그 획득을 **한 번 앞당겨 호출한다** — 소유권을 갖는
> 것이 아니라, 실패를 첫 요청이 아니라 **기동 시점에** 드러내기 위한 fail-fast 장치다.

#### 부트스트랩 절차 (의사코드)

```
ensure_store(db_path):                       # 멱등. 몇 번 불러도 같은 결과
    부모 디렉터리 생성 (없으면)              # app/ratelimit.py:81-84 · app/storage.py:84-85 의 관례
    연결 열기
    PRAGMA journal_mode = WAL                # DB 영속 속성 — 1회로 충분
    PRAGMA synchronous  = NORMAL             # 연결마다
    PRAGMA foreign_keys = ON                 # 연결마다. scripts/load_to_sqlite.py:27 의 관례
    PRAGMA busy_timeout = 5000               # 연결마다. 04 §6.3
    BEGIN IMMEDIATE                          # T4 — 단일 트랜잭션
        CREATE TABLE IF NOT EXISTS sessions / session_auth
        CREATE TABLE IF NOT EXISTS rate_window / rate_known_session / rate_daily
        CREATE TABLE IF NOT EXISTS store_meta
        CREATE INDEX IF NOT EXISTS idx_sessions_last_activity
        INSERT OR IGNORE INTO store_meta(key, value) VALUES ('schema_version', '1')
    COMMIT
```

스키마 본문은 [04 §7.2](./04-interface.md)(`sessions`), [§7.3](./04-interface.md)(`rate_*`),
[§7.4](./04-interface.md)(`session_auth`), [§7.5](./04-interface.md)(`store_meta`)가 이미
확정했다. S1 은 그것을 **옮겨 적기만 한다** — 새 테이블을 발명하지 않는다.

#### 동시 부트스트랩

`--workers N` 에서 N 개 프로세스가 같은 순간에 `ensure_store` 를 부를 수 있다. 세 장치가
그것을 안전하게 만든다: (i) `CREATE ... IF NOT EXISTS` 와 `INSERT OR IGNORE` 가 멱등,
(ii) `BEGIN IMMEDIATE` 가 단일 writer 자리를 시작 시점에 잡아 직렬화, (iii) `busy_timeout`
5000 이 대기 상한을 준다.

**S8 이전에는 워커가 1개라 이 경합이 실제로 발생하지 않는다.** 그래서 S1 에서 멱등하게 써
두지 않으면 결함이 **S8 에서야** 드러난다 — 여덟 단계 중 가장 늦게, 가장 되돌리기 비싼
자리에서. 이것이 S1 에 이 규정을 두는 이유다.

#### 연결 캐시의 키는 **해석된 절대 경로**다

`data/sessions.db` 는 cwd 상대 경로다(`Dockerfile:15-20` 이 이 리포의 모든 데이터 경로가 cwd
상대임을 명시한다). 그런데 `app/knowledge_pack_exercise.py:34`·`scripts/tone_eval.py:117`
등이 실행 중에 `os.chdir` 로 cwd 를 바꾼다.

> **규칙**: 연결은 호출 시점에 해석한 **절대 경로를 키로** 캐시한다. cwd 가 바뀌면 키가 달라져
> 새 연결이 열린다.

- 서버 경로는 cwd 가 고정이므로(`Dockerfile:5` `WORKDIR /app`, `run.py:267` `cwd=REPO_ROOT`)
  프로세스당 연결이 1개다.
- 임시 디렉터리로 chdir 하는 도구 경로는 **그 디렉터리 안의 DB** 를 쓰게 되어 격리가 보존된다
  — S3·S4 가 여기 직접 기댄다(§5·§6).
- [05 §2 반증조건 3](./05-invariants.md)("워커들이 서로 다른 `sessions.db` 를 연다")의 관측
  방법이 그대로 유효하다. 이 규칙은 그 반증을 **숨기지 않는다** — cwd 가 어긋나면 두 번째 DB 가
  실제로 생기고, 그것이 바로 반증조건이 잡으려는 상태다.

### 3.3 S1 의 중단 기준과 롤백

- 중단 기준: §12.1 의 명령이 **209** 를 반환한다. S1 은 호출부가 없으므로 209 가 그대로
  유지되는 것이 정상이다. 209 가 아니면 신규 모듈이 임포트 부작용을 갖고 있다는 뜻이다.
- 추가 확인: `test -f data/sessions.db` 가 **기동 전에는 실패**하고 기동 후 성공한다(부트스트랩
  시점이 설계대로인지의 관측).
- 롤백: 신규 파일 삭제 + 생성된 `data/sessions.db` 삭제. 기존 데이터에 손을 대지 않았으므로
  잔여가 없다.

### 4.2 같은 단계에서 함께 옮겨야 하는 것 — 턴 캡 (T4)

`session.turns` 는 세 곳에서 증가하고(`app/chat.py:325`, `:408`, `:503`) 세 곳에서 판정된다
(`:328`, `:358`, `:505`). 이 여섯 줄은 `_sessions` 를 문자로 포함하지 않아 A축 37 에 잡히지

### 4.4 S2 과도기 규정 — 정의 삭제를 S5 로 미룬다 ★

#### 4.4.1 규정이 없으면 계획이 자기 자신과 모순된다

§2 의 의존 그래프에서 A축 37곳(S3 1 · S4 4 · S5 32)은 **전부 S2 뒤에** 온다. 그런데 S2 가
`app/chat.py:57` 의 정의를 그 자리에서 지우면, 아직 이행되지 않은 그 37곳이 **S2 직후 전부
`AttributeError` 로 깨진다.** `tests/` 안에만 32곳 / 9파일이 남아 있다(§7).

즉 정의 삭제를 S2 에 두면 **S2 의 중단 기준(§12.1 → 209)이 물리적으로 충족 불가능**해지고,
§0 이 세운 "각 단계는 그 단계만으로 209 를 통과한다"는 규율이 첫 실질 단계에서 깨진다.
그 규율은 장식이 아니라 **회귀가 어느 단계에서 났는지 국소화하는 능력 그 자체**다 — 한 번
예외를 두면 S2~S5 구간 전체가 "원래 빨간 상태"가 되어, 그 안에서 새로 생긴 진짜 회귀를
분간할 방법이 사라진다.

> **규정: S2 는 `_sessions` 이름을 지우지 않는다. 그 자리에 읽기 전용 프록시를 남기고,
> 정의의 삭제는 S5 의 종료 조건으로 미룬다.**

#### 4.4.2 프록시의 정확한 성질

| 성질 | 내용 |
|------|------|
| **읽기 전용** | `__getitem__` / `get` / `__contains__` 만 제공한다. 조회는 그때마다 `store.get_session(sid, now)` 로 **위임**하고, 반환값은 `SessionView`(읽기 전용 스냅샷, [04 §1.4](./04-interface.md))다 |
| **쓰기 금지** | `__setitem__` · `update` · `setdefault` 는 **구현하지 않고 즉시 예외를 던진다**(§4.4.4). 오늘 쓰기 형태인 `app/chat.py:82` 는 S2 에서 `open_session` 으로 이미 옮겨졌으므로 남은 쓰기 경로가 없다 |
| **lifecycle 은 위임** | `pop(sid, None)` 만 예외적으로 허용하고 `store.expire_session(sid)` 로 위임한다. S3·S4·S5-g 가 이행되기 전까지 그 7곳이 살아 있어야 하기 때문이다. `clear()` 는 **허용하지 않는다** — §6.1 의 하드 규칙과 같은 이유다(저장소 루트 cwd 에서 도는 세 곳이 실 세션을 지운다). `clear()` 호출 3곳은 S4 가 받을 때까지 §4.4.5 의 과도기 예외로 다룬다 |
| **상태를 갖지 않는다** | 프록시는 dict 를 **감싸지 않는다.** 내부에 캐시·복사본을 두지 않고 매 호출을 스토어로 내려보낸다 |
| **수명** | S2 에서 도입되어 S5 종료와 함께 **삭제된다**(§4.4.3) |

> **"두 표현의 공존"이 아니다.** 프록시는 **저장소를 갖지 않고 스토어를 읽기만 한다.**
> 과도기 어느 시점에도 세션 상태의 진실 원천은 `data/sessions.db` **하나뿐**이며, 프로세스
> 메모리 dict 는 S2 시점에 이미 사라져 있다. 이것이 §8.8 이 다루는 레이트리밋 공존(두 매체가
> 각자의 진실을 갖는 상태)과 결정적으로 다른 점이다 — 여기에는 **동기화할 두 번째 사본이
> 없다.**

#### 4.4.3 프록시는 언제 사라지는가 — S5 의 종료 조건

> **S5 종료 조건**: S5-a~S5-i 아홉 하위 단계가 모두 끝난 뒤, 마지막 하위 작업으로
> **프록시와 `app/chat.py:57` 의 이름 자체를 삭제**하고 §12.1 로 **209** 를 확인한다.
> 이 삭제까지 통과해야 S5 가 완료다.

이 시점에서 A축 37곳이 전부 이행돼 있으므로 프록시를 참조하는 코드가 하나도 남지 않는다.
삭제 후 `grep -rn '\b_sessions\b' app/ scripts/ tests/` 가 **빈 결과**가 되며, 이것이 §10.1
블로커 1 의 판정 기준 그대로다 — **규율을 지키면서 해제 기준도 잃지 않는다.**

#### 4.4.4 프록시가 만드는 위험과 그 차단 ★

프록시의 진짜 위험은 "이행을 덜 한 채로도 초록이 뜬다"는 것이다. 조용히 통과시키면 T3 이
**부분 이행 상태로 고착**되고, 그것이 [05 §8.2](./05-invariants.md)가 지목한 가장 진단하기
어려운 상태다.

| 위험 | 차단 |
|------|------|
| 이행 중 누군가 프록시에 **쓰기**를 시도한다 (`chat._sessions[sid] = ...`) | **조용히 통과시키지 않는다.** `__setitem__` 등은 즉시 예외를 던진다. 실패는 시끄러워야 한다 — 통과시키면 그 쓰기가 스토어에 반영되지 않은 채 사라져 R1 위반을 **무증상으로** 만든다 |
| 프록시가 편해서 이행이 멈춘다 | S5 종료 조건(§4.4.3)이 삭제를 **완료 요건**으로 못박는다. 프록시가 남아 있으면 S5 가 완료되지 않고, S5 가 완료되지 않으면 §10.1 의 블로커 1 판정이 거짓이라 **S8 을 시작할 수 없다** |
| 새 코드가 프록시를 쓰기 시작한다 | 프록시는 S2~S5 구간에만 존재하는 **한시적 장치**임을 코드 주석과 이 문서로 못박는다. 신규 코드는 스토어 연산을 직접 부른다 |
| 프록시를 남긴 채 S8 로 간다 | §10.1 의 판정이 `grep` **빈 결과**를 요구하므로 프록시가 남아 있으면 그 판정이 거짓이 되어 S8 이 차단된다 |

#### 4.4.5 `clear()` 3곳의 과도기 처리

프록시가 `clear()` 를 제공하지 않으므로 `scripts/` 3곳(`tone_eval.py:118`·`:134`,

## 6. S4 — `scripts/` lifecycle 4곳 (A축 4곳)

### 6.1 `.clear()` 를 그대로 옮기면 안 된다 ★

`.clear()` 는 "이 **프로세스의** 세션을 전부 버린다"는 뜻이다. 공유 스토어에는 **같은 의미의
연산이 없고, 있어서도 안 된다** — `clear_all()` 은 다른 워커가 진행 중인 실 세션까지 지운다.

cwd 를 실측하면 네 곳이 두 부류로 갈린다.

| # | 위치 | 그 시점의 cwd | 위험 | 이행 |
|---|------|---------------|------|------|
| 1 | `scripts/tone_eval.py:118` | 임시 디렉터리 (`:117` `os.chdir(tmp)`) | 없음 — 격리됨 | **삭제**. §3.2 규칙 아래서 임시 DB 는 이미 비어 있다 |
| 2 | `scripts/tone_eval.py:134` | **저장소 루트** (`:133` `os.chdir(original_cwd)` **직후**) | **높음** — `clear_all` 로 옮기면 실 세션을 지운다 | 이 스크립트가 만든 `voice-eval-{i}` 세션만 `expire_session` 하거나, 정리를 임시 디렉터리 안(`:133` 이전)으로 옮긴다 |
| 3 | `scripts/red_team_prompt_injection.py:46` | **저장소 루트** (`:15` `os.chdir(REPO_ROOT)`) | **높음** | `redteam-{i:02d}` 세션만 `expire_session` |
| 4 | `scripts/generate_demo_population.py:265` | **저장소 루트** (`:257` `os.chdir(REPO_ROOT)`) | **높음** | 프로필별 `session_id` 만 `expire_session` |

> **S4 의 하드 규칙: 스토어에 `clear_all()` / `truncate()` 계열 연산을 추가하지 않는다.**
> 세 곳(2·3·4)이 저장소 루트 cwd 에서 도는데, 그 편의 연산이 존재하는 순간 "도구를 돌렸더니
> 운영 세션이 사라졌다"가 **한 줄 실수로 도달 가능**해진다. 각 스크립트는 **자기가 만든
> `session_id` 만** 만료시킨다.

다른 29곳과 형태가 다른 유일한 줄이라 S5-h 를 별도 하위 단계로 뒀다.

## 8. S6 — 레이트리밋 이행: `data/ratelimit.json` → `rate_*` 테이블 ★★

### 8.1 결정 — **전량 백필** (사용자 확정)

> **`windows` · `known_sessions` · `daily` 세 구조를 전부 새 테이블로 옮긴다. 리셋하는 항목은
> 없다.**

이 결정은 사용자가 실제 상태 배치를 보고 내렸다. 아래는 그 근거를 실측에 붙여 기록한 것이며,
재론 대상이 아니다.

### 8.2 세 구조와 "리셋했을 때의 비용"

현재 `data/ratelimit.json` 의 실제 형태(`app/ratelimit.py:77` 의 초기 구조와 동일):

| 키 | 형태 | 무엇인가 | 리셋 비용 |
|----|------|----------|-----------|
| `windows` | `{ip: [ISO 타임스탬프, ...]}` | IP별 **신규 세션** 슬라이딩 윈도우. `WINDOW = timedelta(hours=1)`(`:20`), `MAX_SESSIONS_PER_WINDOW = 5`(`:21`) | **작다.** 캡에 걸려 있던 IP 하나당 최대 **5개**의 신규 세션 슬롯이 즉시 회복된다. 1시간 안에 자가 치유된다(윈도우가 슬라이딩이라 옛 항목이 저절로 빠진다, `:106`) |
| `daily` | `{"date", "count"}` | **전역** 일일 요청 카운터. 기본 상한 `daily_cap: int = 500`(`:90`, env `DAILY_REQUEST_CAP`) | **크지만 하루 한정.** 서비스 **전체**가 그날치 예산을 새로 받는다. IP별이 아니라 전역이라 영향 범위가 서비스 전체다 |
| `known_sessions` | `{session_id: ISO}` | **쿼터가 아니다.** 이미 카운트한 `session_id` 집합 — 같은 세션의 후속 발화를 **다시 세지 않게** 하는 이중 카운트 가드(모듈 docstring `:3-4`, `check()` `:97-99`) | **결정적이다.** §8.3 |

### 8.3 `known_sessions` 가 결정적인 이유

`check()` 는 `session_id` 가 `known_sessions` 에 있으면 **그 자리에서 통과**시킨다
(`app/ratelimit.py:98-99`). 이 집합을 리셋하면:

```
컷오버 시점에 3턴째 진행 중이던 사용자
  → 다음 발화가 도착
  → 새 표현의 rate_known_session 에 그 session_id 가 없다
  → "신규 세션"으로 재카운트 (windows[ip] += 1, daily.count += 1)
  → 그 IP 가 이미 1시간 안에 5개를 썼다면 → 429 RATE_LIMIT_MESSAGE
  → 대화 중이던 사용자가 대화 중간에 끊긴다
```

**이 증상이 이 task 가 없애려고 존재하는 바로 그 증상이다.** 세션이 워커·재시작 경계에서
끊기지 않게 만드는 이행이, 그 이행 자체의 컷오버에서 사용자를 끊는다면 자기모순이다.
그래서 `known_sessions` 백필은 선택이 아니다.

`windows`·`daily` 도 함께 옮기는 이유는 **비용이 아니라 일관성**이다 — 세 구조는 같은 JSON
파일 한 개에서 나오고 같은 트랜잭션에 들어간다. 일부만 옮기면 얻는 절감이 사실상 0 인데
(§8.4 의 파싱은 어차피 파일 전체를 읽는다) 두 부류의 코드 경로가 생긴다.

### 8.4 기각한 두 대안과 그 비용

| 안 | 이득 | 대가 | 판정 |
|----|------|------|------|
| (A) **전량 리셋** | 이행 스크립트가 아예 필요 없다. 컷오버가 "새 빈 테이블로 시작"이라 가장 단순하다 | `known_sessions` 유실 → §8.3 의 증상. 게다가 `daily` 리셋으로 그날 전역 예산 500 이 통째로 회복되고, 캡에 걸려 있던 모든 IP 가 각각 5슬롯을 회복한다 | **기각** — 이 task 의 목적과 정면 충돌 |
| (B) **부분 백필** (`known_sessions` 만) | 결정적 증상은 막는다. 옮길 행 수가 가장 적다 | `windows`·`daily` 리셋으로 (A) 의 쿼터 회복이 그대로 남는다. 백필/비백필 두 경로가 한 트랜잭션 안에 섞여 이행 스크립트의 검증 표면이 넓어진다. 그런데 절감은 거의 없다 — 세 구조가 같은 파일에서 같이 파싱된다 | **기각** — 대가 대비 이득이 없다 |
| **(C) 전량 백필 — 채택** | §8.3 의 증상이 없고, 쿼터 회복이 없고, 코드 경로가 하나다 | 이행 스크립트가 필요하다. 손상된 JSON 을 만나면 컷오버가 멈춘다(§8.5 — 이것은 대가가 아니라 의도된 안전 장치다) | **채택 (사용자 확정)** |

### 8.5 레거시 JSON 파싱 규정 — 없음 / 손상 / 부분 / 원소

| 상황 | 판정 | 근거 |
|------|------|------|
| **파일 없음** | **정상.** 빈 상태로 시작하고 `backfilled = 0` 을 기록한 뒤 계속 진행한다 | 오늘 `_load()` 가 `os.path.exists` 로 정확히 같은 판단을 한다(`app/ratelimit.py:76-77`). 신규 배포·클론 직후가 이 경우다 |
| **JSON 파싱 실패 (손상)** | **중단.** 이행 트랜잭션을 커밋하지 않고 컷오버를 진행하지 않는다. **자동 복구·자동 삭제 금지** | [04 §1.2](./04-interface.md)의 `CORRUPT` 방침과 동일. 손상 파일을 조용히 빈 상태로 대체하면 (A) 전량 리셋을 사고로 실행하는 셈이다 |
| **최상위 키 누락** (`windows`/`known_sessions`/`daily` 중 일부 없음) | **정상.** 없는 키는 빈 것으로 취급하고 계속 진행한다 | 오늘 `check()` 가 `setdefault` 로 같은 처리를 한다(`:97`, `:104`, `:113`). 옛 버전이 쓴 파일이 이 형태다 |
| **최상위 키 타입 어긋남** (`windows` 가 dict 아님, `daily` 가 dict 아님 등) | **중단.** 손상과 동일 취급 | 타입이 어긋난 것은 "옛 포맷"이 아니라 손상이다. 조용히 건너뛰면 그만큼이 리셋된다 |
| **개별 원소 이상** (파싱 불가 ISO 문자열, dict 아닌 타임스탬프 목록, 형식 위반 `session_id`, 정수 아닌 `count`) | **그 원소만 건너뛰고 건수를 기록한다.** 스킵이 1건이라도 있으면 이행 리포트에 표시하고 **운영자 확인 후** 컷오버를 마친다 | 원소 하나 때문에 전체를 막으면 실무에서 (A) 로 도망가게 된다. 다만 조용히 넘기지도 않는다 |

**이행은 단일 `BEGIN IMMEDIATE` 트랜잭션 안에서 수행한다**(T4). 중단 판정이 나면 `COMMIT`
자체가 없으므로 **부분 반영 상태가 남지 않는다.**

### 8.6 매핑

| 레거시 | 새 테이블 | 규칙 |
|--------|-----------|------|
| `windows[ip] = [ts, ...]` | `rate_window(ip, seen_at)` | 타임스탬프 1개 = 1행. PK `(ip, seen_at)` 이므로 중복은 `INSERT OR IGNORE` 로 자연 병합된다 |
| `known_sessions[sid] = ts` | `rate_known_session(session_id, first_seen_at)` | 1:1. `INSERT OR IGNORE` |
| `daily = {"date": d, "count": n}` | `rate_daily(day, count)` | 1행. `INSERT OR IGNORE` |

**만료된 윈도우 항목을 이행 스크립트가 미리 걸러내지 않는다.** 1시간이 지난 항목은 첫
`check_rate` 호출이 어차피 무시하고 정리한다(오늘 `:106` 과 같은 판정). 스크립트가 시간
판정을 하면 **스냅샷 시각과 실제 컷오버 시각의 차이만큼** 잘못 자르게 된다 — 판정은 런타임에
맡기는 쪽이 항상 옳다.

`daily.date` 가 컷오버 날짜와 다르면 그 행은 그대로 들어가고 `rate_daily` 에 오늘 행이 없는
상태가 된다. 이는 오늘 `check()` 의 날짜 롤오버 처리(`:114-116`)와 **같은 결과**다 — 새 날의
카운트는 0 에서 시작한다. 옛 행을 남기는 것은 감사·롤백용이다.

### 8.7 컷오버 순서 — **정지 컷오버**를 택한다

```
1. 옛 프로세스 중지                       ← 이 시점부터 JSON 에 새 쓰기가 없다
2. data/ratelimit.json 스냅샷 복사        ← 롤백 근거 보존 (§8.8)
3. 백필 트랜잭션 1회 (BEGIN IMMEDIATE)    ← §8.5 의 중단 판정이 여기서 걸린다
4. 새 프로세스 기동
5. 중단 기준 확인 (§12.1 → 209)
```

**왜 정지 컷오버인가**: 이 서비스는 단일 호스트·단일 워커 배포이고(`Dockerfile:30`), 무중단이
요구된 적이 없다. 정지 컷오버는 §8.8 의 공존 창을 **0 으로** 만든다 — 아래에서 보듯 창이
0 이 아니면 손실이 반드시 생기며, 그 손실을 없애는 다른 방법이 없다.

### 8.8 공존 구간 — 창이 0 이 아닐 때 무슨 일이 일어나는가

무중단 롤링 재시작(새 컨테이너 기동 → 헬스체크 → 옛 컨테이너 종료)을 택하면, 그 구간에서
옛 코드(JSON)와 새 코드(테이블)가 **동시에 살아 있다. 두 표현은 서로를 보지 않는다.**

| 방향 | 무슨 일이 일어나나 | 결과 |
|------|--------------------|------|
| 옛 → 새 | 옛 워커가 JSON 에 기록한 신규 세션 카운트가 새 테이블에 없다 | 그 구간의 요청 수만큼 **레이트리밋이 느슨해진다** |
| 새 → 옛 | 새 워커가 테이블에 기록한 것이 JSON 에 없다 | **롤백하면 그 구간이 사라진다**(§8.9) |
| 공통 | 같은 사용자가 두 표현 중 어느 쪽에 붙느냐가 라우팅에 달린다 | `known_sessions` 판정이 요청마다 달라질 수 있어 **중간 429** 가 가능하다 |

**상한**: (공존 창 길이) × (유입률). 창이 몇 초면 실무적으로 무시할 수 있지만 **0 은 아니다.**
정직하게 적는다.

무중단이 반드시 필요하다면 다음을 규정한다.

1. 공존 창의 **길이 상한을 미리 정하고**(권고: 60초) 초과 시 컷오버를 중단·롤백한다.
2. 옛 프로세스가 완전히 종료된 **직후** 백필을 한 번 더 수행한다. 백필이 전부
   `INSERT OR IGNORE` 이므로 **멱등**이고, 두 번째 실행이 창 동안의 델타를 흡수한다.
3. 그래도 남는 잔여(창 동안 새 표현에만 기록된 것)는 방향이 "레이트리밋이 느슨해지는 쪽"
   하나로 고정된다 — 사용자를 끊지 않는 방향이다.

**이중 쓰기(dual-write)는 기각한다.** 이행 기간 동안 JSON 과 테이블에 동시에 쓰면 두 매체를
원자적으로 묶어야 하고, 그 문제는 [04 §6.4](./04-interface.md)가 대화 파일에 대해 이미
다뤘다 — 묶이지 않는다. 게다가 `BEGIN IMMEDIATE` 트랜잭션 안에 파일 read-modify-write 를 다시
넣게 되어 임계 구역 규율([04 §6.3](./04-interface.md))을 정면으로 위반한다.

### 8.9 S6 롤백

- **트리거**: §12.1 이 209 미만 / 429 응답 급증 / `CONFLICT` 로그 관측.
- **절차**: 새 프로세스 중지 → 옛 커밋으로 기동. `data/ratelimit.json` 은 **지우지 않았으므로**
  옛 코드가 그 상태 그대로 즉시 동작한다.
- **손실**: 컷오버 이후 새 테이블에만 쌓인 카운트. JSON 은 컷오버 시점에 얼어 있다. 방향은
  "레이트리밋이 느슨해지는 쪽"이고, 상한은 (롤백까지의 시간 × 유입률)이며, 슬라이딩 윈도우가
  1시간이라 **최대 1시간 안에 자가 치유**된다.
- **재이행 멱등**: 백필이 전부 `INSERT OR IGNORE` 이므로 다시 돌려도 중복 행이 생기지 않는다.

### 8.10 `data/ratelimit.json` 을 언제 지우는가

[04 §7.1](./04-interface.md)은 이 파일을 "폐기 예정 (Phase 6)"으로 적었다. **여기서 정한다:
S6 은 지우지 않는다.**

삭제는 **S8 완료 + 관측 기간(권고 7일) 이후**의 별도 정리 단계로 미룬다. 근거는 §8.9 다 —
롤백 경로가 그 파일에 기댄다. 롤백 근거를 컷오버와 같은 단계에서 지우는 것은 안전망을 쓰기
직전에 치우는 일이다.

### 8.11 `rate_known_session` 보존 정책

[04 §7.3](./04-interface.md)이 이 정책을 Phase 6 으로 넘겼다.

> **이행 단계에서는 오늘 시맨틱을 그대로 보존한다 — 만료시키지 않는다.**

오늘 `known_sessions` 는 만료 개념이 없다(`check()` 가 지우는 코드가 없다). 이행의 1차 의무는
시맨틱 보존이고, 여기에 만료를 새로 도입하면 **이행이 아니라 정책 변경**이 된다 —
`rate_known_session` 을 `sessions` 에 흡수하지 않기로 한 [04 §7.3](./04-interface.md)의 근거와
같은 이유다(D03 의 24시간 TTL 에 묶이면 레이트리밋이 느슨해진다).

**성장률 상한**: 전역 일일 캡 500(`app/ratelimit.py:90`) × 365 = 연 최대 약 **182,500행**.
행당 수십 바이트이므로 연 수 MB 규모다. 이행 기간에 문제되지 않는다. 별도 정리 정책은 이행
완료 후의 결정으로 남긴다.

### 8.12 S6 의 중단 기준

- §12.1 → **209**.
- 추가: 백필 직후 행 수 대조 — `rate_window` 행 수 = 스냅샷의 타임스탬프 총 개수 − 스킵 수,
  `rate_known_session` 행 수 = 스냅샷의 `known_sessions` 키 수 − 스킵 수. 불일치는 즉시 롤백.

> **규정**: S7 은 **런타임 쓰기 경로 9곳만** 옮긴다. `app/storage.py:71` 의 함수는 남는다.
> 삭제 여부는 이 task 범위 밖이다.
>

### 9.4 S6 을 먼저 하기를 권고하는 이유 ([05 §9](./05-invariants.md) 미결 3번)

(B) 보존안 아래서 파일이 담는 턴 수는 **`20 + F`** 이고, `F`(COMMIT 실패로 남은 미커밋
append 수)를 묶는 것은 `MAX_TURNS = 10`(`app/chat.py:15`)이 **아니라 D04 레이트리밋**이다
([05 §5.4](./05-invariants.md)) — 실패한 append 는 `turns` 를 증가시키지 않지만 요청 하나는
소비하기 때문이다.

그 상한이 **워커 횡단으로** 성립하려면 레이트리밋이 이미 새 표현(S6)에 있어야 한다. 강제
선행은 아니다 — S8 이전에는 워커가 1개라 오늘의 JSON 레이트리밋도 상한을 준다. 다만 S6 ≺ S7
이면 그 논거가 처음부터 성립한다.

> **구현 금지 사항**: 파일 크기를 "세션당 상수"로 하드코딩하지 말 것. 상한의 출처는 세션당
> 상수가 아니라 **요청률 상한**이다.

### 9.5 [05 §9](./05-invariants.md) 미결 2번을 여기서 수용 판정한다

**미결**: 고아가 남은 날짜에 이후 append 가 없으면 그 파티션이 `turn_partitions` 에 영영
들어가지 않아 `turn_days` 완전성이 조건부가 된다.

**판정: 수용한다.** 그 파티션의 인덱스 인정 개수는 0 이므로 `restore_history` 는 그 날짜 파일을
**아예 열지 않고**, 결과는 국면 ①의 잘라내기 `turns[:0]` 과 동치다 — 고아가 모델 컨텍스트에
들어가지 않는다. 방향이 fail-closed 이고, 안전성(차단된 발화의 부활 없음)은 무사하며 **완전성만
조건부**가 된다. [05 §7.2](./05-invariants.md)가 같은 성격의 구멍에 내린 판정과 동일하다.

**세션 재개 시 1회 점검을 도입하는 안은 기각한다** — 읽기 경로에 디렉터리 스캔을 넣게 되어
[04 §6.3](./04-interface.md)의 임계 구역 금지 목록("`data/conversations/*` 디렉터리 전수
스캔")을 위반한다. **감사 기록은 어느 쪽이든 대화 JSON 파일에 그대로 남는다.**

## 10. S8 — `--workers 1` 해제 (`Dockerfile:30`)

### 10.1 해제 조건 — 블로커 3건이 **전부** 해소돼야 한다

`Dockerfile:25-29` 의 사유 주석은 두 가지를 든다(`RateLimiter` 의 프로세스 내부 락, `_sessions`
프로세스 메모리 dict). 여기에 블로커 3(동시 쓰기 유실, `app/storage.py:71`)을 더한 **3건 전부**가
해제 조건이다.

| 블로커 | 위치 | 해소 단계 | **관측 가능한 판정 기준** |
|--------|------|-----------|---------------------------|
| 1. 세션 상태 | `app/chat.py:57` | S1·S2·S3·S4·S5 (**S5-z 포함**) | `grep -rn '\b_sessions\b' app/ scripts/ tests/` 가 **빈 결과**. 정의 줄까지 사라져야 한다 — 그 삭제가 곧 S5-z(§4.4.3)이므로, **과도기 프록시가 남아 있으면 이 판정이 거짓이 되어 S8 이 차단된다** |
| 2. 레이트리밋 | `app/ratelimit.py:63`, 주석 `:66-68` | S1·S6 | `grep -rn 'ratelimit.json\|threading.Lock' app/` 가 **빈 결과** |
| 3. 대화 쓰기 | `app/storage.py:71` | S1·S7 | `grep -rn 'storage\.append_turn' app/` 가 **빈 결과** (함수 정의는 남는다, §9.3) |

세 판정이 **전부** 참이고 §12.1 이 **209** 일 때만 S8 을 시작한다.

> **조건 없이 숫자만 바꾸자는 제안은 CAP21 이 지목한 fake-satisfy 다.** 세 판정 중 하나라도
> 거짓이면 워커를 늘리는 순간 그 경로에서 옛 동작이 재현되고, 재현이 간헐적이라 진단이 특히
> 어렵다([05 §8.2](./05-invariants.md)).

### 10.2 S8 이 실제로 바꾸는 것

1. `Dockerfile:30` 의 `--workers` 값.
2. **`Dockerfile:25-29` 의 사유 주석.** 주석은 두 블로커를 근거로 워커 고정을 설명한다 — 숫자만
   바꾸고 주석을 남기면 문서가 코드와 어긋난 채 다음 사람에게 인계된다. 주석 갱신은 선택이
   아니다.
3. `app/ratelimit.py:66-68` 의 "단일 uvicorn 워커 전제" 주석(CAP19). 같은 이유다.

### 10.3 S8 의 중단 기준과 롤백

- 중단 기준: §12.1 → **209**. **추가로 `--workers 2` 이상에서** §14 의 e2e 시나리오 4종을
  실행해 통과를 확인한다. pytest 는 단일 프로세스라 워커 횡단 결함을 **구조적으로 볼 수 없다**
  ([07 §2.2](./07-compatibility-review.md)가 이 한계를 이미 기록했다) — 209 만으로 S8 을
  판정하면 이 이행의 목적 자체를 검증하지 않은 셈이 된다.
- 롤백: `Dockerfile` 의 숫자를 1 로 원복하고 재배포. 데이터 이행이 없으므로 잔여가 없다.
- **중간 단계에서 워커를 늘려 "확인해 보는" 것을 금지한다.** S2~S7 중 어느 지점에서든 워커를
  늘리면 아직 이행되지 않은 경로가 그대로 노출된다.

## 12. 중단 기준과 롤백 총칙

### 12.1 중단 기준 — 이 형태를 그대로 쓴다

각 단계(및 S5-a~S5-z·S7 의 각 하위 단계) 직후, **저장소 루트 기준으로** 다음을 실행해 **209**
를 확인한다.

```bash
"$(git rev-parse --show-toplevel)/.venv/bin/python" -m pytest -q
```

> **209 passed 가 아니면 다음 단계로 넘어가지 않는다. 그 자리에서 되돌린다.**

**이 기준에 예외를 두는 단계는 없다.** "S2~S5 구간은 원래 빨간 상태"라는 예외를 한 번
허용하면, 그 구간 안에서 **새로 생긴 진짜 회귀를 분간할 방법이 사라진다** — 이 이행 계획이
단계를 잘게 쪼갠 이유 전체가 무효가 된다. S2 가 정의를 지우지 않고 과도기 프록시를 남기는
것(§4.4)이 바로 그 예외를 만들지 않기 위한 장치다.

**이 형태를 문자 그대로 쓰는 이유**(후속 구현 task 가 같은 함정을 물려받지 않도록):

- 맨몸 `python` 에는 **pytest 가 설치돼 있지 않다.** 반드시 저장소 venv 인터프리터를 쓴다
  ([01 §6](./01-current-state.md)).
- `.venv/bin/python` 같은 **상대 경로는 cwd 에 따라 깨진다.** `git rev-parse --show-toplevel`
  로 저장소 루트를 확정한 절대 경로를 쓴다.
- **209** 는 [01 §6](./01-current-state.md)이 실측으로 확정한 회귀 기준선이며 CAP37 이 요구하는
  숫자다. 이행이 전부 끝난 뒤에도 이 숫자가 유지되어야 한다([04 §8](./04-interface.md)).

### 12.2 단계별 롤백 요약

| 단계 | 롤백 방법 | 데이터 잔여 | 되돌림 난이도 |

## 13. Phase 5 의 두 전제를 이 계획이 어떻게 갚는가

### 13.1 T3 — 37곳 + 9곳 전건 이행

[05 §8.2](./05-invariants.md)는 T3 을 이렇게 못박았다: **"부분 이행은 부분 달성이 아니라 어떤
요청 경로에서는 옛 결함이 그대로 살아있는 상태"** 이며, 그 상태는 재현이 간헐적이라 진단이
특히 어렵다.

이 계획이 갚는 방식:

1. §11.1 이 37곳을 **라인 단위로** 배정한다 — "대충 테스트 쪽"이 아니라 파일:라인이다.
2. §11.2 가 **세 방향(파일별·단계별·성격별)으로 검산**한다. 한 방향만 맞추는 실수를 잡는다.
3. §11.3 이 B축 9곳을 따로 닫는다.
4. §10.1 의 판정 기준이 `grep` **빈 결과**를 요구한다 — "옮겼다고 생각한다"가 아니라 관측이다.
5. **S5-z(§4.4.3)가 그 관측을 실행 가능한 시험으로 바꾼다.** 과도기 프록시를 걷어낸 직후의
   209 는 "37곳이 전건 이행됐다"의 **직접 검사**다 — 하나라도 남아 있으면 그 자리에서
   `AttributeError` 로 드러나고, 프록시가 그것을 감춰 줄 수 있는 마지막 순간이 거기다.

### 13.2 T4 — `BEGIN IMMEDIATE` 단일 트랜잭션 · R1 · R2

이 계획의 어느 단계도 R1·R2 를 위반하는 중간 상태를 만들지 않는다.

| 단계 | 위반 위험 | 이 계획의 방어 |
|------|-----------|----------------|
| S1 | 부트스트랩이 여러 트랜잭션으로 쪼개짐 | §3.2 절차가 `BEGIN IMMEDIATE` 하나 |
| S2 | 편의상 `save(session)` 를 두고 싶어진다 (R1 위반) | §4.2 — 갱신은 전부 부분 갱신 인자. 턴 캡은 `consume_turn` 의 `WHERE` 절(R2) |
| S2~S5 (과도기) | 프록시가 **쓰기 가능한 dict 처럼** 구현되어 R1 을 되살린다 | §4.4.2 — 프록시는 읽기 전용이고 상태를 갖지 않는다. `__setitem__` 계열은 예외를 던진다(§4.4.4). 조회는 매번 `get_session` 위임이라 갱신 경로가 존재하지 않는다 — **모든 갱신은 여전히 스토어의 `BEGIN IMMEDIATE` 안에서만 일어난다** |
| S4 | `clear_all()` 편의 연산 추가 | §6.1 하드 규칙 — 추가 금지 |
| S6 | 백필을 여러 트랜잭션으로 나눔 / dual-write | §8.5 단일 트랜잭션, §8.8 dual-write 기각 |
| S7 | 파일 교체를 트랜잭션 밖에서 수행 | [04 §6.2](./04-interface.md) 임계 구역 경계를 그대로 따른다 |

**S6 이 특히 위험하다** — "이행 스크립트니까 트랜잭션 규율은 좀 느슨해도 되지 않나"가 자연스러운
오독이다. 그렇지 않다: 백필이 부분 반영되면 §8.3 의 증상이 **일부 사용자에게만** 발생해
진단이 가장 어려운 형태가 된다.

## 14. 후속 e2e 인계

이 task 는 문서 전용이라 e2e 매칭이 **공집합**이다(`e2e_refs: []`). 그러나 구현 task 가 `app/`
을 건드리는 순간 아래 시나리오가 매칭된다. 미리 지목해 인계한다.

| 시나리오 | 카탈로그의 파일 지문 | 트리거하는 단계 | 왜 걸리나 |
|----------|----------------------|-----------------|-----------|
| `chat-session-auth` | `app/main.py`, `app/chat.py`, `app/storage.py` | **S2**, S7 | `has_session`/`owns_session`/`session_token` 세 줄이 전부 바뀐다. 401 두 분기의 의미가 재정의된다 |
| `chat-injection-guardrail` | `app/safety.py`, `app/chat.py`, `app/addiction.py` | **S7**, S2 | `app/chat.py:405` 의 `exclude_from_context = True`(§9.2)가 차단된 발화의 컨텍스트 격리를 결정한다 |
| `chat-korean-roundtrip` | `app/chat.py`, `app/main.py`, `app/storage.py`, `app/llm.py`, `app/prompting.py`, `static/*` | **S2**, S7 | 정상 대화 왕복 전 구간. UTF-8 고정 계약([04 §7.6](./04-interface.md))의 실경로 확인 |
| `ratelimit-new-session-cap` | `app/ratelimit.py`, `app/main.py` | **S6** | 컷오버가 정확히 이 시나리오의 판정 대상(신규 세션 캡)을 건드린다 |

- **S1** 도 `app/` 에 신규 파일을 추가하므로 매칭이 시작된다. 다만 호출부가 없어 동작 변화가
  없다.
- **S8** 은 `Dockerfile` 만 바꾸므로 파일 지문으로는 어느 시나리오와도 겹치지 않는다. 그래서
  §10.3 이 **워커 2 이상에서 네 시나리오를 명시적으로 실행**할 것을 별도로 요구한다 — 지문
  매칭에만 기대면 이 이행의 목적을 검증하는 유일한 관문이 조용히 비게 된다.

## 15. 이 계획이 **정하지 않은** 것

정직하게 남긴다. 아래는 구현 task 또는 별도 결정의 몫이다.

| 항목 | 왜 여기서 정하지 않나 |
|------|------------------------|
| 실제 컷오버 **승인**과 실행 시각 | 운영 판단이다. 이 문서는 절차와 롤백만 정한다([영향 범위](../../planning/session-store-multiworker/phase-06-migration-plan.md)) |
| `rate_known_session` 의 **장기** 정리 정책 | 이행 중에는 시맨틱 보존이 1차 의무다(§8.11). 성장률 상한만 기록했다 |
| `storage.append_turn` 함수 자체의 삭제 | 209 기준선이 그 함수를 직접 테스트한다(§9.3). 삭제는 이 task 범위 밖 |
| 스토어 도입 시점의 기존 `data/conversations` 파일 처리 | 포맷이 D05 로 **유지**되므로 이행이 필요 없다. 기존 파일은 그대로 읽힌다. 다만 그 파일들에 대한 `turn_partitions` 초기값은 0 이며, §9.5 의 fail-closed 판정이 그 상태를 안전하게 닫는다 |
| `synchronous = FULL` 전환 | [05 §9](./05-invariants.md) 6번 — 범위 밖. 필요 시 신규 결정 |

## 16. 이 페이즈가 만들지 않은 것 (CAP04·CAP08·CAP09)

이 문서를 쓰면서 **다음을 만들지 않았고 실행하지 않았다.**

- 스키마 파일(`.sql`) — §3.2 의 SQL 은 [04 §7](./04-interface.md)을 인용한 **설계 표기**다.
- 프로토타입 스토어 모듈 — `data/` 에 `chatlog.db` 외의 SQLite 파일이 생기지 않았다.
- 이행 스크립트 — §8 은 스크립트의 **규정**이지 스크립트가 아니다.
- 기동 스크립트·설정 변경 — `Dockerfile`·`run.py` 는 인용 대상일 뿐 수정 대상이 아니다.

**스토어를 "확인 삼아" 한 번 돌려보는 것이 이 task 의 가장 흔한 실패 모드이고**, phase 검증의
`NO-PROTOTYPE-STORE-OK` 게이트가 그 흔적을 잡는다.
