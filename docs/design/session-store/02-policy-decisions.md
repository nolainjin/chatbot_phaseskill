## D01. 세션 스토어 백엔드

### 질문

세션 상태(현재 `app/chat.py:57`의 `_sessions: dict[str, ChatSession] = {}` 모듈 전역 dict)를
어떤 스토어로 옮길까? 판단 기준에 "비개발자가 클론 후 바로 실행"이 깨지지 않을 것을 반드시
포함한다.

### 후보 비교와 권고안

| 후보 | 신규 런타임 의존성 | 클론 후 바로 실행 | 동시성 모델 | 수평 확장 |
|------|---------------------|---------------------|--------------|-----------|
| **① SQLite(stdlib `sqlite3`, WAL), 기존 `/app/data` 볼륨, 로컬·Docker 동일 백엔드 — 권고안** | 0 | 유지 | 동일 호스트 멀티프로세스, WAL 직렬화 writer | 불가(전환점 명시, 아래 대가 참고) |
| ② Redis 필수 의존 | 패키지 1 + 별도 서비스 | 깨짐(서비스 기동 필요) | 원자적 카운터, 네이티브 TTL | 가능 |
| ③ 로컬=메모리/파일, Docker=Redis 이중 백엔드 | 배포 시 1(서비스) | 유지(로컬만) | 백엔드별 상이 | Docker 경로만 가능 |
| ④ 파일 + 크로스플랫폼 파일락 직접 구현 | 0 | 유지 | fcntl/msvcrt 수동 분기 | 불가 |

**권고안은 ①이며, 확정 답도 ①이다.**

### 확정 답

SQLite(표준 라이브러리 `sqlite3`, WAL 모드)를 기존 `/app/data` 볼륨에 두고, 로컬 실행과 Docker
배포가 **동일 백엔드**를 쓴다.

### 근거

- 신규 런타임 의존성 0, 신규 서비스 0 — `run.py`의 클론 후 바로 실행 경험이 그대로 유지된다.
  `run.py`는 `argparse`/`os`/`subprocess`/`sys`/`threading`/`time`/`webbrowser`/`pathlib`만
  import하며 서드파티 의존이 전혀 없다(실측 확인).
- "비개발자가 클론 후 바로 실행"이라는 판단 기준은 이 결정에서 **장래 주장이 아니라 현재
  관측**이다 — `sqlite3`는 이미 이 리포의 살아있는 의존이다:
  - `app/stats.py:6` `import sqlite3` — `GET /api/stats`가 이미 SQLite를 읽어 통계를 만든다.
  - `scripts/load_to_sqlite.py`가 존재하며 일배치로 SQLite에 적재한다.
  - `deploy/README.md:26-27`이 "`data/` 디렉토리(컨테이너 경로 `/app/data`) 하나에
    `ratelimit.json`, `conversations/YYYY-MM-DD/*.json`, `chatlog.db`가 전부 들어간다"고
    명시한다 — 세션 스토어 DB 파일을 같은 볼륨에 추가하는 것은 새 인프라가 아니라 기존
    구성의 연장이다.
- WAL 모드는 "동일 호스트 멀티프로세스" 동시 접근을 정확히 지원한다 — `uvicorn --workers N`
  실행 모델과 정확히 일치하고, 워커 재시작도 견딘다.
- windows/macos/ubuntu 3-OS CI 매트릭스 전부에서 추가 서비스 없이 그대로 동작한다.
- 배포 형상(단일 `/app/data` 볼륨, `Dockerfile:21` `VOLUME ["/app/data"]`)과 부합한다.
- 인터페이스를 뽑아두면(D06, Phase 4 소관) 장래 Redis 어댑터로 교체할 자리가 남는다.

### 기각된 후보와 사유

- **② Redis 필수 의존** — 네이티브 TTL(`EXPIRE`)과 원자적 카운터로 세션 만료·레이트리밋이
  가장 깔끔하게 풀리고 다중 인스턴스 수평 확장도 열리지만, 런타임 패키지 + 별도 서비스 기동을
  동시에 요구해 "클론 후 바로 실행"이 깨진다. GitHub Actions service container는 Linux 러너
  전용이라 windows/macos 레그에서 스토어 경로가 미검증으로 남아 3-OS 가드가 비대칭이 된다 —
  이 레포는 윈도우 전용 실패를 이미 두 차례 별도 커밋으로 고쳤다(`1e9d900`, `19ffb76`). 배포
  비용도 증가한다.
- **③ 로컬/배포 이중 백엔드** — origin이 명시적으로 검토 대상으로 올렸으므로 검토했고,
  기각 사유를 여기 남긴다(누락 시 CAP27이 조용히 잘림). 로컬 실행 경험을 지키면서 배포는
  확장 가능하게 두는 장점이 있으나, 두 코드 경로를 각각 유지·검증해야 하고 "로컬에서는
  절대 재현되지 않는 배포 전용 버그"라는 계열이 새로 생긴다. 이 레포가 지금까지 가장 비싸게
  고친 실패 유형이 정확히 그 계열이다(크로스플랫폼 실행 경로 정비 커밋 `1e9d900`/`19ffb76`/
  `c5adc0c`). 백엔드별 동시성 시맨틱 차이(원자성·TTL)가 설계 문서를 두 벌로 만들어 이후
  Phase 4/5/7의 논증 비용도 두 배가 된다. **권고하지 않는다.**
- **④ 파일 + 크로스플랫폼 파일락 직접 구현** — 의존성 0을 유지하지만 `fcntl`(POSIX)/
  `msvcrt`(Windows) 분기를 직접 떠안는데, 크로스플랫폼 파일락은 이 레포에서 가장 깨지기 쉬운
  영역이고 실질적으로 DB를 다시 만드는 일이다. 209 기준선 대비 회귀 위험이 후보 중 가장 크다.

### 대가와 한계 — 수평 확장 전환점

SQLite 채택의 한계는 다음 지점에서 수평 확장(멀티 인스턴스)이 막힌다는 것이며, 이 지점을 넘는
확장이 필요해지면 그때가 Redis 등 외부 스토어로 전환할 시점이다:

- **writer는 항상 1개** — SQLite는 WAL 모드에서도 한 시점에 커밋 가능한 writer가 1개다. 모든
  쓰기(세션 갱신, 레이트리밋 카운트, 대화 턴 append)가 이 단일 writer에서 직렬화된다.
- **동일 호스트 전용** — 컨테이너를 여러 대(멀티 인스턴스)로 늘리는 수평 확장은 이 설계로는
  불가능하다. `uvicorn --workers N`(단일 호스트 멀티프로세스)까지만 지원 범위다.
- **네트워크 파일시스템 불가** — NFS 등 네트워크 파일시스템 위에서는 SQLite의 파일락 보장이
  깨져 사용할 수 없다. 블록 디바이스(로컬 디스크 또는 블록 스토리지 볼륨) 위에서만 유효하다.
- 배포 볼륨이 실제로 블록 디바이스인지 확인하는 작업은, 선행 task(`docs/planning/
  lmwiki-chatbot-proto`)의 호스팅 플랫폼 결정이 아직 확정되지 않아 지금 확인할 대상 자체가
  없다 — 이는 이번 D01 결정(SQLite 채택)을 미루는 것이 아니라, 이미 확정된 이번 결정에 딸린
  후속 검증 항목을 호스팅 플랫폼이 정해지는 시점으로 이월하는 것이다. 그 시점이 오면 마운트된
  볼륨 종류를 확인해 이 한계가 실제로 저촉되는지 판정한다.

## D02. 개인정보 경계 (요약 — 전담은 Phase 3)

### 확정 답

`ChatSession`의 최소 상태만 세션 스토어에 저장한다: `session_id`(스토어 키) +
`session_token`/`turns`/`slots`/`last_question_slot_id`/`participant_id` — 값 필드 5개, 합계
6/7 필드. `history`(대화 원문)는 세션 스토어에 넣지 않고, 필요 시 기존
`data/conversations/YYYY-MM-DD/{session_id}.json`에서 복원한다.

### 근거 요약

대화 원문의 사본이 하나(대화 JSON)로 유지되어 개인정보 표면이 늘지 않는다.
`docs/security-review.md#5`의 미해결 FOLLOW-UP(보존기간·삭제요청·암호화·고지)이 세션 스토어와
대화 JSON 두 시스템으로 번지지 않는다는 것이 실질 이득이다. 대가는 복원 경로를 새로 만들어야
한다는 것과, `append_turn` 호출 대비 `history.append` 대응이 없는 비대칭 5건([01-current-state.md
§5.2](./01-current-state.md#5-append_turn--historyappend-비대칭-지도--날짜-파티션))을 정밀
대조해야 한다는 것이다 — 이 대조를 빠뜨리면 복원된 컨텍스트가 원본과 미묘하게 달라진다.

### 상호 참조

복원 경로의 구체 설계, 비대칭 5건과의 정밀 대조, `security-review.md §5` 연계는
`docs/design/session-store/03-history-restore.md`(Phase 3)가 전담한다. 옵션 전체 비교와
트레이드오프는 [decisions.md#D02](../../planning/session-store-multiworker/decisions.md)를
참고한다.

## D03. 세션 TTL

### 질문

세션 만료를 어떻게 정의할까? 현재는 만료 개념이 없고 프로세스 재시작이 유일한 정리 수단이다.

### 확정 답

마지막 활동(last-activity) 기준 고정 TTL **24시간** + 요청 경로(request-path) lazy sweep.

### 근거

- **24시간 확정 수치**: 상담 세션이 마지막 활동으로부터 24시간을 넘기면 만료로 간주한다.
  브라우저를 닫았다가 같은 날 또는 다음 날 아침 돌아오는 정상 사용 패턴을 수용하면서도 무기한
  보존을 피하는 값이다. 이 숫자는 현재 재시작이 담당하던 정리(재시작마다 세션 전량 소실)를
  대체하는 보존기간 상한이며, `docs/security-review.md §5 (a)` 보존기간 요건에 대한 첫 답이
  된다.
- **청소 메커니즘(lazy sweep)**: 별도 백그라운드 프로세스나 크론을 새로 두지 않는다. 대신
  세션 스토어에 접근하는 요청 경로(`has_session`/`owns_session`/`_get_session` 계열 조회) 안에서
  조회 대상 레코드의 last-activity가 24시간을 넘겼으면 그 자리에서 만료 처리(삭제)한다. 숫자만
  확정하고 이 sweep을 빠뜨리면 스토어가 무한 증가해, 재시작이 하던 정리보다 나쁜 회귀가 된다 —
  이 메커니즘은 24시간 값과 분리할 수 없는 한 쌍이다. sweep을 SessionStore 인터페이스의 구체
  메서드로 명세하는 작업은 Phase 4(D06 인터페이스 재설계)가 담당한다.
- 워커 수와 무관하게 동작한다 — sweep 판정이 매 요청마다 스토어 조회 시점에 일어나므로 워커
  프로세스가 여러 개여도 각 워커가 독립적으로 같은 규칙을 적용하면 된다.

### 대가와 한계

- 24시간은 정책 값으로서 이 문서에 근거와 함께 고정한다. 향후 법무 검토에서 값이 바뀔 수
  있으나, 그 변경은 이 결정을 뒤집는 것이 아니라 같은 정책의 파라미터 조정이다.
- lazy sweep은 **접근이 있어야만** 정리가 일어난다 — 만료 이후 다시는 접근되지 않는 세션은
  다음 접근이 없는 한 스토어에 계속 남는다(원 스펙이 요구한 "재시작이 담당하던 정리의 대체"라는
  목표는 만족하지만, 완전한 보존 상한을 강제하지는 않는다). 접근 없는 만료 레코드까지 확실히
  청소해야 한다면 별도 배치가 추가로 필요하며, 그 배치의 설계는 이번 결정 범위 밖이다.

## D04. 레이트리밋 배치

### 질문

레이트리밋 상태를 세션과 같은 스토어에 둘까, 분리할까?

### 확정 답

같은 스토어(같은 DB, 별도 테이블) — 세션 쓰기와 레이트리밋 쓰기를 **하나의 트랜잭션 경계** 안에
둔다.

### 근거 — 워커 수에 비례해 느슨해지지 않음을 트랜잭션 경계로 논증

- **현재 위험**: `app/ratelimit.py:63` `class RateLimiter`는 `threading.Lock`(프로세스 내부
  락) + 로컬 JSON 파일의 read-modify-write(`app/ratelimit.py:90` `def check` → `_load`로 읽고
  `_save`에서 `os.replace`로 원자적 교체)로 카운터를 관리한다. `threading.Lock`은 같은 프로세스
  안의 스레드만 배제하므로, 워커가 여러 개(별도 프로세스)가 되면 워커마다 독립된 락을 갖고
  같은 JSON 파일에 각자 read-modify-write를 수행한다 — 두 워커가 거의 동시에 읽고 각자 갱신값을
  쓰면 나중 쓰기가 앞선 쓰기를 덮어써 카운트가 유실된다(lost update). 이 상태로 워커를 N개로
  늘리면 IP당 5회 제한과 일일 캡이 최악의 경우 N배까지 느슨해질 수 있다 — `Dockerfile:25-29`가
  `--workers 1` 고정 사유로 정확히 이 문제를 지목한다.
- **해결**: 레이트리밋 상태를 세션과 같은 DB의 별도 테이블로 옮기고, "현재 카운트 확인 →
  캡 초과 여부 판정 → 카운트 증가"의 세 단계를 SQLite 트랜잭션 하나로 묶는다. SQLite는 동일
  DB 파일에 대해 한 시점에 커밋 가능한 writer가 1개다(WAL 모드에서도 writer는 직렬화된다) —
  즉 이 세 단계가 워커 프로세스 수와 무관하게 원자적 단위로 실행된다. 두 워커가 동시에 같은
  IP의 카운트를 증가시키려 해도, 트랜잭션 직렬화 때문에 한쪽이 커밋을 마친 뒤에야 다른 쪽이
  최신 카운트를 읽는다 — lost update가 구조적으로 발생하지 않는다. 이것은 "대략 시행"이나
  "결과적 일관성"이 아니라 트랜잭션 경계에 의한 정확한 시행이다. 이 논증을 완화(대략 시행,
  결과적 일관성)로 바꾸는 것은 사용자 승인 없이는 할 수 없는 결정 축소다.
- 이 논증은 IP당 5회 슬라이딩 윈도우 제한과 전역 일일 캡(`daily_cap`) 양쪽에 동일하게
  적용된다 — 둘 다 같은 read-modify-write 패턴이고 같은 트랜잭션 경계 안에 들어가기 때문이다.

### 대가와 한계

- `data/ratelimit.json`의 lost update는 DB 트랜잭션으로 실제로 해결되는 대신, 레이트리밋
  쓰기가 세션 쓰기와 같은 단일 writer를 두고 경합한다 — SQLite는 한 시점에 writer가 1개이므로
  세션 쓰기 트랜잭션과 레이트리밋 쓰기 트랜잭션이 서로를 기다릴 수 있다. 요청당 쓰기 횟수가
  적어(레이트리밋 카운트는 신규 세션 생성 시점에만 증가하고, 같은 세션의 후속 발화는
  `known_sessions`에 걸려 통과한다) 실측 부하는 낮을 것으로 보이나, 정확한 측정은 Phase 5
  (불변식 논증)가 수행한다.
- 동시성 정확성을 한 번만 증명하면 되므로(세션과 레이트리밋이 같은 트랜잭션 모델을 공유) 검증
  비용은 낮다. 백업·볼륨 정책도 하나로 유지된다.

### 기각된 후보

- **분리(별도 파일/백엔드)**: 쓰기 경합이 분산되고 장애가 격리되지만, 동시성 정확성을 두 번
  증명해야 하고 두 저장소의 백업·마운트 정책이 갈라진다 — 검증·운영 비용이 는다.
- **이번 범위에서 제외하고 `--workers 1` 유지**: 설계 범위가 줄어 빨라지지만, origin이 블로커
  4건 중 하나로 명시했고 이를 남기면 `Dockerfile:30`의 `--workers 1`을 풀 수 없어 이 task의
  목표(다중 워커 지원) 자체가 달성되지 않는다.

## D05. 대화 쓰기 동시성

### 질문

`append_turn()`이 세션 JSON 전체를 재작성해 생기는 동시 쓰기 턴 유실을 어떻게 막을까?

### 확정 답

JSON 포맷은 그대로 두고, 쓰기를 세션 스토어의 트랜잭션/락으로 직렬화한다.

### 근거

- `app/storage.py:71` `def append_turn(...)`은 오늘 날짜 디렉터리의 세션 JSON을
  읽고(`path.read_text`) → 메모리에서 turn을 append(`turns.append(...)`) →
  파일 전체를 다시 쓰는(`path.write_text`) read-modify-write다. 두 요청이 거의 동시에 같은
  세션에 대해 `append_turn`을 호출하면 나중에 쓴 쪽이 앞선 쪽의 turn을 덮어써 턴이 유실될 수
  있다([01-current-state.md §1](./01-current-state.md#1-블로커-4건) 블로커 3).
- **포맷을 유지하는 이유** — 이 JSON 포맷의 소비자가 5곳이다: `app/storage.py` 자신,
  `app/stats.py`(SQLite 적재용 판독), `scripts/load_to_sqlite.py`(배치 적재),
  `scripts/generate_demo_population.py`, `scripts/smoke_local.sh`. 포맷을 바꾸면 5곳을 전부
  손봐야 하고 기존 `data/` 파일 마이그레이션이 따라와 209 기준선 회귀 위험이 커진다.
- **직렬화 방식** — 세션 스토어(D01에서 SQLite로 확정)가 세션 단위 트랜잭션/락 지점을 이미
  제공한다(D04와 같은 메커니즘). `append_turn` 앞뒤로 이 트랜잭션/락을 걸어 "같은 세션에 대한
  파일 read → append → write" 전체를 하나의 임계 구역으로 묶는다. 별도의 새 동시성
  프리미티브를 도입하지 않고 기존 트랜잭션 경계를 재사용한다.

### 대가와 한계

- **파일 쓰기(디스크 I/O)가 DB 락 수명에 묶인다** — 임계 구역 안에서 파일 읽기·쓰기까지
  수행하므로 락을 쥐고 있는 시간이 길어진다. 같은 세션 또는 스토어 전역 락 범위에 걸리는 다른
  접근이 이 파일 I/O 시간만큼 대기할 수 있다.
- 경로가 한 겹 복잡해진다 — 순수 DB 트랜잭션이 아니라 "DB 락 + 파일 I/O"가 한 임계 구역에
  섞인다.
- 임계 구역의 구체 설계(락 획득 범위가 세션별인지 스토어 전역인지, 락 종류)는 Phase 4
  (SessionStore 인터페이스)가 정한다. 정확성 논증(교착 없음, 재진입 안전성 등)은 Phase 5
  (불변식 논증)가 담당한다. 이 문서는 결정과 그 근거까지만 고정한다.

### 기각된 후보

- **대화 턴도 DB로 옮기고 JSON은 내보내기 산출물로 강등**: 동시성이 근본적으로 해결되고 배치
  적재가 단순해지지만, 소비자 5곳을 전부 손봐야 하고 기존 `data/` 파일 마이그레이션이
  따라온다. 209 기준선 회귀 위험이 가장 크고, "설계 문서만 만든다"는 이번 범위 대비 파급이
  과하다.
- **append-only JSONL로 포맷 변경**: 추가 쓰기가 원자적이 되어 유실이 사라지고 재작성 자체가
  없어지지만, 포맷 변경이라 소비자 5곳 + 기존 `data/` 마이그레이션이 따라오고 현재 payload의
  `schema_version`/`participant_id` 헤더 구조를 다시 설계해야 한다.
