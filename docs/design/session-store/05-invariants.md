# 세션 스토어 분리 — Phase 5: 목표 달성 논증 (불변식 I1~I6)

> 이 문서는 **결론**을 산출하는 자리다. Phase 1 은 현황을 **서술**했고 Phase 6 은 이행
> **절차**를 짤 것이며, 둘 중 어느 것도 "그래서 origin 의 목표가 달성되는가"를 답하지 않는다.
>
> 입력 문서: [Phase 1 현황 분석](./01-current-state.md), [Phase 2 정책 결정](./02-policy-decisions.md)
> (D01·D03·D04·D05), [Phase 3 개인정보 경계와 `history` 복원](./03-history-restore.md)(D02,
> 해소안 (다), `(day, seq)` 전역 순서), [Phase 4 `SessionStore` 인터페이스](./04-interface.md)
> (연산 집합, `BEGIN IMMEDIATE` 임계 구역, 성질 P1, 꼬리 폐쇄성).
>
> 이 문서 작성으로 저장소 코드는 **한 줄도 바뀌지 않는다**(CAP04·CAP08·CAP09).
>
> **각 불변식은 「주장 / 논증 / 반증 조건」 세 칸으로 쓴다.** 무엇이 관측되면 이 논증이 틀린
> 것인지 적지 않은 주장은 검증 불가능한 선언일 뿐이며, 이 문서에서는 논증으로 치지 않는다.

## 0. 판정 요약

origin 의 최상위 목표는 **"세션 상태를 프로세스 메모리에서 분리해 다중 워커와 서버 재시작을
견디게 만든다"**이다. 여섯 불변식이 그 목표를 분해한다.

| # | 불변식 | 주장 한 줄 | 대응 CAP | 판정 |
|---|--------|-----------|----------|------|
| **I1** | 워커 횡단 동일성 | 요청이 어느 워커로 가도 같은 세션 상태를 읽고, 모든 쓰기가 하나의 전순서에 들어간다 | CAP01 | 성립 (T1·T3·T4 조건부) |
| **I2** | 401 분기 도달불가 | `app/main.py:43-48` 의 거짓 401 은 살아있는 세션에 대해 **도달 불가**가 된다 | CAP12 | 성립 |
| **I3** | 재시작 내구성 | 프로세스 종료·재기동 후에도 세션이 살아 있고 진행 중 사용자가 막히지 않는다 | CAP02·CAP13 | 성립 (T2·T5 조건부) |
| **I4** | 대화 쓰기 직렬화 정확성 | 같은 세션에 두 워커가 동시에 써도 턴이 유실되지 않는다 | CAP20 | 성립 (T3·T4 조건부) |
| **I5** | 인증·캡의 워커 횡단 정확성 | 발급된 토큰은 어느 워커에서도 통하고, 10턴 캡은 워커마다가 아니라 세션당 한 번 성립한다 | CAP14·CAP15 | 성립 |
| **I6** | 복원 history 의 안전 경계 | 쓰기 시점에 차단된 발화는 복원된 `history` 에 들어갈 수 없다 | CAP29 계열 | 안전 방향 성립 / 완전성은 **조건부** (§6.2) |

**종합 판정과 그 전제는 §8 에 있다.** 요약하면: 목표는 **설계 수준에서 달성되며**, 다섯 전제
(T1~T5)가 이행 단계에서 유지된다는 조건이 붙는다. 그중 T3(37곳 + 9곳 이행 완결)은 Phase 6 이
책임지는 항목이고, 그것이 깨지면 I1 과 I4 가 **국소적으로** 거짓이 된다.

## 1. 여섯 논증이 공유하는 전제

같은 근거를 여섯 번 반복하지 않기 위해 여기 한 번만 세운다. 아래 전제 중 하나가 이행에서
깨지면 그 전제를 쓰는 불변식이 함께 깨진다 — 각 불변식의 「반증 조건」이 이 전제들을 다시
지목하는 이유다.

| 전제 | 내용 | 근거 |
|------|------|------|
| **P-매체** | 세션 상태는 `data/sessions.db`(SQLite, WAL) 한 파일에 있고, 그 파일은 기존 `/app/data` 볼륨에 있다. 범위는 **동일 호스트 멀티프로세스**(`uvicorn --workers N`)이며 멀티 인스턴스·네트워크 파일시스템은 범위 밖 | D01([02 §D01](./02-policy-decisions.md#d01-세션-스토어-백엔드)), [04 §7.1](./04-interface.md), `Dockerfile:21` `VOLUME ["/app/data"]` |
| **P-직렬화** | SQLite 는 한 시점에 커밋 가능한 writer 가 1개이고, 모든 갱신 연산은 `BEGIN IMMEDIATE` 로 그 자리를 트랜잭션 시작 시점에 잡는다 | D01 "대가와 한계", [04 §4.3](./04-interface.md), [04 §6.1](./04-interface.md) |
| **P-API** | R1: 스토어 밖에서 레코드를 읽어 고쳐 되쓰는 API(`put`/`save`)가 **없다**. R2: 판정은 `WHERE` 절로 내려가고 결과는 영향 행 수로 돌아온다 | [04 §1.3](./04-interface.md) |
| **P-시간** | `now` 는 모든 연산이 **인자로 받는다**. 스토어 안에서 `date.today()`/`datetime.now()` 를 부르지 않으므로 한 요청 안에서 시간 기준이 두 번 평가되지 않는다 | [04 §1.5](./04-interface.md), Phase 3 §5.2 의 자정 경합 |
| **P-경계** | `history` 는 스토어에 없다. 복원은 `data/conversations/{day}/{sid}.json` 에서 `turn_partitions` 가 지목한 날짜만 열어 조립한다 | D02, [03 §5](./03-history-restore.md), [04 §1.5 #8](./04-interface.md) |

> **논증의 대상은 설계다.** 이 문서는 Phase 2·3·4 가 확정한 설계가 목표를 달성함을 논증하며,
> 아직 존재하지 않는 구현이 그 설계를 따랐음을 논증하지 않는다. 그래서 모든 「반증 조건」은
> **이행 이후에 관측 가능한 형태**로 적었다 — 이 문서는 Phase 6 의 수용 기준이기도 하다.

## 2. I1 — 워커 횡단 동일성

### 주장

`uvicorn --workers N`(N ≥ 2)에서, 같은 `session_id` 에 대한 요청이 **어느 워커로 라우팅되든**
같은 세션 상태를 관측한다. 구체적으로 (a) **읽기 경로**: 임의의 두 워커가 같은 시점에 관측하는
세션 상태는 동일한 커밋 상태다. (b) **쓰기 경로**: 모든 상태 변경이 하나의 **전순서(total
order)** 에 들어가며, 어떤 변경도 다른 변경을 조용히 덮어쓰지 않는다.

I1 은 **재시작에 대해 아무것도 주장하지 않는다.** 그것은 I3 의 몫이며, 두 성질이 독립임은
§4 에서 반례로 보인다.

### 논증

**오늘 무엇이 깨지는가.** `_sessions: dict[str, ChatSession]`(`app/chat.py:57`)는 **모듈 전역
dict** 다. `uvicorn --workers N` 은 프로세스를 N 개 포크하므로 dict 도 N 벌이 되고, 워커 A 가
만든 `ChatSession` 은 워커 B 의 dict 에 존재하지 않는다. 이 사실이 `Dockerfile:28-29` 가
`--workers 1` 을 고정한 두 사유 중 하나로 명시돼 있다.

**읽기 경로.** 새 설계에서 세션 상태의 소재는 프로세스 힙이 아니라 `data/sessions.db` 파일
하나다(P-매체). `--workers N` 이 만드는 N 개 프로세스는 **같은 호스트의 같은 파일**을 연다.

```
워커 A ─┐
워커 B ─┼─▶ data/sessions.db  (WAL)  ─▶  sessions / session_auth / rate_* 테이블
워커 C ─┘        └ 같은 /app/data 볼륨, 같은 inode
```

- WAL 모드(`04 §7.2`)에서 읽기는 쓰기와 동시에 진행되며, 읽는 쪽은 **마지막으로 커밋된 상태**의
  일관된 스냅샷을 본다. 즉 워커 B 는 워커 A 의 절반만 반영된 상태를 볼 수 없다.
- 조회 계열 연산(`get_session` / `verify_owner` / `open_session` / `restore_history`,
  [04 §1.5](./04-interface.md))은 전부 이 파일을 원천으로 삼는다. 워커별 캐시·복제본이 설계에
  존재하지 않으므로 "워커마다 다른 답"이 나올 자리가 없다.
- `history` 만은 스토어 밖에 있다(P-경계). 그래서 읽기 경로의 동일성은 두 매체에 대해 각각
  성립해야 한다 — 대화 JSON 역시 같은 `/app/data` 볼륨의 같은 파일이고, **어느 날짜 파일을
  열지**는 워커의 기억이 아니라 스토어의 `turn_partitions` 가 결정한다([03 §3.3](./03-history-restore.md)).
  따라서 두 워커의 복원 결과는 같은 인덱스에서 같은 파일을 열어 같은 필터를 적용한 결과로
  일치한다.

**쓰기 경로.** 동일성은 "같은 것을 읽는다"만으로 성립하지 않는다. 두 워커가 각자 읽어 각자
고쳐 각자 쓰면 읽기는 일관되어도 상태는 갈라진다.

- P-API 의 R1 이 그 형태 자체를 없앤다: `put(record)` / `save(session)` 같은 전체 덮어쓰기 API 가
  설계에 **존재하지 않는다.** 갱신은 "무엇을 어떻게 바꿀지"를 인자로 받고 스토어 내부 트랜잭션
  안에서 읽고 고치고 쓴다([04 §1.3](./04-interface.md)).
- P-직렬화가 그 트랜잭션들을 한 줄로 세운다. `BEGIN IMMEDIATE` 는 트랜잭션 시작 즉시 단일
  writer 자리를 잡으므로, 두 갱신은 겹칠 수 없고 하나가 끝난 뒤 다른 하나가 시작한다.
- 결과: 상태 변경의 **전순서**가 존재하고, 모든 워커가 그 순서의 접두사를 본다. 이것이
  "워커 횡단 동일성"의 정확한 내용이다 — 동시에 같은 값을 본다는 뜻이 아니라, **모두가 같은
  하나의 이력을 본다**는 뜻이다.

**이 논증이 의존하는 이행 조건 (T3).** `_sessions` 를 **거치지 않고 dict 를 직접 만지는 접근이
37곳 / 13파일** 있다([01 §2](./01-current-state.md)). 그중 하나라도 이행되지 않고 남으면 그
경로는 프로세스 로컬 상태를 읽고 쓰므로 **그 지점에서 I1 이 국소적으로 거짓**이 된다. 특히
`app/knowledge_pack_exercise.py:37` 의 `chat._sessions.pop(...)` 은 애플리케이션 코드이므로
테스트 전용이 아니다. 이행 절차는 Phase 6 소관이며, 이 문서는 그것을 I1 의 **전제**로 못박는다.

### 반증 조건

무엇이 관측되면 I1 이 거짓인가.

1. 이행 완료 후 `grep -rn '\b_sessions\b' app/ scripts/` 가 비어 있지 않다 — 스토어를 우회하는
   프로세스 로컬 상태 접근이 남았다는 직접 증거다.
2. 같은 살아있는 세션·같은 토큰으로 보낸 두 요청이 **워커에 따라 다른 `turn` 값**을 돌려준다.
3. 워커들이 서로 다른 `data/sessions.db` 를 연다. `Dockerfile:18-20` 이 "모든 기본 경로가 cwd
   상대"라고 명시하므로, cwd 가 `/app` 이 아닌 워커가 하나라도 있으면 **두 번째 스토어가 조용히
   생긴다.** 관측: 실행 중 `find / -name 'sessions.db'` 결과가 1개가 아니다.
4. 볼륨이 NFS 등 네트워크 파일시스템이다(D01 이 명시적으로 배제한 조건) — SQLite 파일락 보장이
   깨져 P-직렬화가 무너진다.
5. 컨테이너를 2대 이상으로 늘린 멀티 인스턴스 구성에서 I1 을 기대한다 — 이것은 **반증이 아니라
   범위 밖**이다. D01 이 지원 범위를 단일 호스트로 확정했다. 구분해서 기록한다.
6. 어떤 갱신 경로가 `SessionView` 를 읽어 고친 뒤 통째로 되쓰는 형태로 구현된다(R1 위반) —
   두 워커의 갱신이 서로를 덮어쓴다.

## 3. I2 — 401 분기 도달불가

### 주장

`app/main.py:47-48` 의 401 `"만료된 세션입니다. 새 세션으로 시작해 주세요."` 는 **살아있는
세션에 대해 도달 불가**가 된다. 여기서 "살아있는 세션"은 **스토어에 레코드가 있고
`now - last_activity_at ≤ 24h`(D03)** 인 세션을 뜻한다.

### 논증

#### 3.1 먼저 세워야 하는 전제 — `conversation_exists()` 의 조회 범위

이 전제를 빼면 자정을 넘긴 세션에 대한 결론이 **틀린다.**

> `conversation_exists()`(`app/storage.py:29-36`)는 **오늘 날짜 디렉터리만** 조회한다.
> `app/storage.py:35` 가 `Path(base_dir) / date.today().isoformat() / f"{session_id}.json"` 의
> `is_file()` 을 그대로 돌려준다. 어제 이전 날짜의 대화 파일이 아무리 많아도 **오늘 파일이
> 없으면 `False`** 다.

`append_turn`(`app/storage.py:71`)도 같은 기준으로 쓴다 — `:84` `day_dir = Path(base_dir) /
date.today().isoformat()`. 즉 "오늘 파일이 있다" ⟺ "오늘 이 세션에 대해 `append_turn` 이 최소
1회 실행됐다"이다.

이 전제를 잘못 세우면(예: `conversation_exists()` 가 전체 날짜를 스캔한다고 가정하면) "자정을
넘긴 세션도 401 로 끊긴다"는 **거짓 결론**이 나온다. 실제로는 §3.2 의 4행이 보이듯 401 이 아니라
**조용한 세션 초기화**가 일어난다 — 증상이 다르고, 따라서 해소 논증도 달라야 한다.

#### 3.2 오늘의 분기 — 네 조합을 하나씩

`app/main.py:43-48` 의 진입부는 다음 세 술어의 조합이다.

```
:43   session_was_known = chat.has_session(session_id)
:44-46  if session_was_known:  if not chat.owns_session(...):  → 401 "세션 인증이 필요합니다."
:47-48  elif storage.conversation_exists(session_id):          → 401 "만료된 세션입니다. ..."
```

| # | `has_session` | `owns_session` | `conversation_exists` | 결과 | 살아있는 세션에서 언제 발생하나 |
|---|---|---|---|---|---|
| 1 | True | True | (미평가) | 통과 | 정상 — 이 워커가 세션을 기억하고 토큰이 맞을 때 |
| 2 | True | False | (미평가) | 401 인증 | 토큰이 틀렸을 때. **의도된 401** 이며 거짓 401 이 아니다 |
| 3 | **False** | (미평가) | **True** | **401 만료** | ← **거짓 401.** 아래 (g1)·(g2) |
| 4 | **False** | (미평가) | False | 통과 (신규 취급) + 새 토큰(`:58-59`) | ← **조용한 초기화.** 아래 (g3) |

`has_session()`(`app/chat.py:60-61`)은 `session_id in _sessions` 다. 살아있는 세션인데 이 값이
`False` 가 되는 생성원은 셋뿐이다.

- **(g1) 다른 워커가 만들었다** — `_sessions` 가 프로세스별이므로(`app/chat.py:57`) 요청이 다른
  워커로 라우팅되면 즉시 `False`. 오늘 이 세션이 한 번이라도 말했으면 `conversation_exists()` 는
  `True` 이므로 **3행 = 거짓 401**. 이것이 CAP12 가 지목한 경로다.
- **(g2) 프로세스가 재기동됐다** — 모듈 전역 dict 가 프로세스와 함께 사라진다
  (`app/chat.py:1-5` docstring 이 "재시작 시 소실은 프로토타입 수용 범위"라고 명시). 같은 날
  안이면 역시 **3행 = 거짓 401**. 이것이 CAP13 이다.
- **(g3) (g1) 또는 (g2)인데 오늘 아직 말하지 않았다 (자정 넘김)** — 어제 23:00 에 마지막 발화,
  지금 01:00. D03 의 24시간 TTL 기준으로는 **살아있는 세션**이지만 오늘 디렉터리에 파일이
  없으므로 `conversation_exists()` 는 `False` → **4행**. 401 은 나지 않는다. 대신
  `turns`·`slots`·`history` 가 모두 초기값인 **새 세션**으로 처리되고, `app/main.py:58-59` 가
  **새 토큰까지 발급**한다. 사용자에게는 "상담이 처음으로 되돌아간 것"으로 보인다.

**(g1)/(g2) 와 (g3)은 상호배타다** — 같은 세션에 대해 오늘 발화가 있으면 3행, 없으면 4행이다.
즉 오늘의 코드에는 **두 개의 서로 다른 결함**이 날짜 경계를 사이에 두고 나뉘어 있다. §3.1 의
전제 없이는 이 사실 자체가 보이지 않는다.

#### 3.3 새 설계에서 각 행이 어떻게 되는가

Phase 4 §3 이 네 공개 함수를 **폐기 2 / 대체 2** 로 처리한다.

| 오늘 | 새 설계 | 근거 |
|------|---------|------|
| `has_session`(`app/chat.py:60`) | **폐기.** `open_session` 의 `created` 플래그에 흡수 — "존재 확인"이라는 독립 왕복 자체가 사라진다 | [04 §3](./04-interface.md) |
| `owns_session`(`app/chat.py:64`) | **대체.** `verify_owner(session_id, token, now)`. `secrets.compare_digest`(`app/chat.py:69`) 상수시간 비교는 유지 | [04 §1.5 #3](./04-interface.md) |
| `storage.conversation_exists`(`app/storage.py:29`) | **요청 경로에서 호출되지 않는다.** 만료 판정의 오라클은 스토어 레코드의 `last_activity_at` 단독 | [04 §1.2](./04-interface.md) |

그러면 각 행은 이렇게 된다.

- **3행(거짓 401) — 술어 자체가 사라진다.** 401 `"만료된 세션입니다."` 는 이제 `Err(EXPIRED)`
  에서만 나온다. `EXPIRED` 의 발생 조건은 [04 §1.2](./04-interface.md)가 정의한 대로
  **"레코드가 있었으나 `now - last_activity_at > 24h` 라서 이 호출이 그 자리에서 삭제했다"**
  하나뿐이다. 살아있는 세션은 정의상 이 조건을 만족하지 않는다. 그리고 "메모리엔 없는데 오늘
  파일은 있다"는 상태는 **더 이상 어떤 술어로도 검사되지 않으므로** 401 을 만들 수 없다 —
  고쳐진 것이 아니라 **분기가 제거된 것**이다.
- **1·2행 — 유지된다.** 살아있는 세션에 대해 `open_session` 은 `created = False` 와 실재하는
  행을 돌려주고, 토큰이 맞으면 200, 틀리거나 없으면 401 `"세션 인증이 필요합니다."`
  ([04 §4.4](./04-interface.md) 토큰 응답 규정). 후자는 **의도된 인증 실패**이며 I2 의 주장
  대상이 아니다. I2 는 "만료 문구 401"에 대한 주장이지 "모든 401"에 대한 주장이 아니다.
- **4행(조용한 초기화) — 함께 사라진다.** 판정 기준이 **날짜 디렉터리**에서 **타임스탬프**로
  바뀌기 때문이다. `last_activity_at`(`04 §2.3`)은 ISO 8601 UTC 시각이고 TTL 은 그 시각으로부터
  24시간이다. 자정은 이 계산에서 아무 의미가 없다. 어제 23:00 마지막 활동 + 지금 01:00 이면
  경과 2시간이므로 `open_session` 은 기존 행을 그대로 돌려주고 `created = False` 다 —
  `turns`·`slots` 가 보존되고 새 토큰도 발급되지 않는다.

#### 3.4 도달불가의 정리

> **살아있는 세션(레코드 존재 ∧ `now - last_activity_at ≤ 24h`)에 대해 401 `"만료된
> 세션입니다."` 를 만드는 경로가 설계에 존재하지 않는다.**

논증 골자: 그 문구를 내는 유일한 원인은 `Err(EXPIRED)` 이고(§3.3), `EXPIRED` 의 발생 조건은
`now - last_activity_at > 24h` 이며, 이는 "살아있는 세션"의 정의와 **직접 모순**이다. 워커 수와
재기동 횟수는 이 조건에 등장하지 않으므로, 조건의 참·거짓이 워커나 프로세스 수명에 의존하지
않는다. (g1)·(g2)·(g3)이 만들던 세 경로는 술어 자체가 요청 경로에서 제거되면서 함께 사라진다.

**미결 지점 하나를 숨기지 않는다.** [04 §4.4](./04-interface.md)의 토큰 응답 규정 표에는
`created = True` 인데 **클라이언트가 (오래된) 토큰을 제시한** 경우의 행이 없다. 만료된 세션이
`open_session` 안에서 삭제·재생성되면 정확히 그 상태가 된다. 두 해소(① 새 세션으로 200+새
토큰, ② 401 `"만료된 세션입니다."`) 중 어느 쪽을 택하든 **I2 의 결론은 바뀌지 않는다** — 두
경우 모두 **살아있지 않은** 세션에 대해서만 발동하기 때문이다. 다만 사용자에게 보이는 문구가
달라지므로 Phase 6 이 이 행을 명시적으로 채워야 한다(§9 인계).

### 반증 조건

1. 어떤 요청이 401 `"만료된 세션입니다."` 를 받은 시점에 `SELECT last_activity_at FROM sessions
   WHERE session_id = ?` 가 행을 돌려주고 `now - last_activity_at ≤ 24h` 다 → **I2 직접 반증**.
2. 이행 완료 후 `grep -rn 'conversation_exists' app/main.py app/chat.py` 가 비어 있지 않다 →
   요청 경로에 옛 판정 오라클이 남아 §3.3 의 전제가 깨진다.
3. 자정 직후 요청에서 응답의 `turn` 이 0 으로 리셋되거나 응답에 새 `session_token` 이 실린다 →
   4행(조용한 초기화)이 살아남았다.
4. 같은 살아있는 세션·같은 토큰의 연속 요청이 워커에 따라 200/401 로 갈린다 → I1 의 반증이자
   I2 의 반증(워커별로 다른 스토어를 보고 있다).
5. 두 워커가 넘기는 `now` 가 24시간 이상 어긋난다 → 한 워커는 살아있다고, 다른 워커는
   만료됐다고 판정한다. P-매체가 단일 호스트를 전제하므로 정상 구성에서는 발생하지 않지만,
   `now` 생성을 워커 밖(예: 클라이언트 제출값)으로 옮기면 즉시 발생한다.
6. `EXPIRED` 가 같은 `session_id` 에 대해 **반복 관측**된다 → lazy sweep 이 같은 호출 안에서
   레코드를 지운다는 [04 §1.2](./04-interface.md)의 일회성 규정이 지켜지지 않고 있다는 뜻이며,
   만료 판정이 다른 곳(예: 파일 존재)에 의존한다는 신호다.

## 4. I3 — 재시작 내구성

### 주장

프로세스가 종료되고 다시 기동된 뒤에도 (a) 세션 레코드가 남아 있고, (b) 진행 중 사용자가 401 로
막히지 않으며, (c) `turns`·`slots`·`session_token` 이 보존되고, (d) `history` 가 복원된다.

**주장의 범위**: "프로세스 종료·재기동"은 SIGTERM/배포 교체/워커 리로드/애플리케이션
프로세스 크래시(SIGKILL 포함)를 뜻한다. **호스트 전원 상실·OS 크래시는 이 주장의 범위가
아니다** — 사유는 §4.3.

### 논증 — 재시작은 별도 시나리오다

I3 을 I1 의 따름정리로 처리하지 않는다. 재시작은 **공유성에 더해 내구성**을 요구하고, 그 둘은
독립이기 때문이다. 먼저 그 독립성을 반례로 확정한다.

#### 4.1 "공유이지만 휘발성인 스토어" 반례 — I1 은 성립하고 I3 는 실패한다

CAP02 의 적대적 노트가 정확히 이 실패 모드를 경고한다. 세 가지 구체 반례를 세운다. **세 반례
모두 I1 을 완전히 만족시키면서 I3 만 깬다.**

| 반례 | I1 (워커 횡단) | I3 (재시작) | 왜 그런가 |
|------|----------------|-------------|-----------|
| (v1) tmpfs 위의 `sessions.db` | **성립** — 같은 호스트의 모든 워커가 같은 파일을 연다. 파일락·WAL·트랜잭션이 전부 정상 작동한다 | **실패** | tmpfs 는 메모리 파일시스템이라 호스트/컨테이너 재생성 시 내용이 사라진다 |
| (v2) 컨테이너 쓰기 가능 레이어 위의 `sessions.db`(볼륨 미마운트) | **성립** — 같은 컨테이너 안의 워커들에게는 동일한 파일이다 | **실패** | 컨테이너를 새로 만들면(이미지 교체·재배포) 레이어가 초기화된다 |
| (v3) 영속 설정 없는 외부 캐시(예: 디스크 저장 끈 Redis) | **성립** — 공유·원자성·네이티브 TTL 까지 얻는다 | **실패** | 프로세스가 죽으면 데이터가 없다. 게다가 **스토어 프로세스 재시작**이라는 새 실패 지점이 생긴다 |

세 반례의 공통점: **매체를 공유하는 것만으로는 재시작을 견디지 못한다.** I3 를 떠받치는 것은
"공유"가 아니라 매체의 **내구성**이다. 따라서 I1 의 논증(§2)을 그대로 재사용할 수 없고, 별도
논증이 필요하다.

#### 4.2 시나리오 R — 4턴 진행 중 재기동

```
t0  사용자가 세션 s1 로 4턴 진행. 응답에서 받은 토큰 K 를 브라우저가 보관.
t1  배포/리로드/크래시로 프로세스 종료.
t2  프로세스 재기동.
t3  사용자가 같은 s1, 같은 토큰 K 로 5번째 발화를 보낸다.
```

**오늘 t3 에서 무슨 일이 일어나는가.** `_sessions`(`app/chat.py:57`)는 프로세스와 함께 사라졌다.
`app/main.py:43` `has_session()` 은 `False`. 같은 날이면 오늘 파일이 있으므로 `:47-48` 이 401
`"만료된 세션입니다."` (§3.2 의 3행 = CAP13). 자정을 넘겼으면 401 은 없지만 4행의 조용한
초기화가 일어나 `turns=0`, `slots={}`, 새 토큰이다. 어느 쪽이든 4턴이 사라진다.

**새 설계에서 t3.** 단계별로 짚는다.

1. **레코드가 남아 있다 (a).** 세션 상태의 소재가 프로세스 힙이 아니라 `data/sessions.db`
   파일이다(P-매체, [04 §7.1](./04-interface.md)). 프로세스 종료는 파일을 건드리지 않는다.
   재기동 시 스키마 초기화는 `CREATE TABLE IF NOT EXISTS`([04 §7.2](./04-interface.md))이므로
   기존 행을 지우지 않는다 — `DROP`/`CREATE` 가 아니라는 점이 여기서 load-bearing 이다.
2. **TTL 판정이 프로세스 수명과 무관하다.** 만료 기준은 `last_activity_at` 과 `now` 의 차이
   (D03, [04 §2.3](./04-interface.md))이지 "프로세스가 이 세션을 기억하는가"가 아니다. t0 의
   마지막 활동이 24시간 이내면 t3 에서 세션은 **살아있다**. 오늘은 재시작이 곧 정리 수단이었고
   (`app/chat.py:1-5`), 새 설계는 그 역할을 TTL 이 넘겨받는다.
3. **401 로 막히지 않는다 (b).** `open_session(s1, now)` 은 행을 찾아 `created = False` 를
   돌려주고, 재조회로 얻은 `session_auth` 행의 토큰(성질 P1, [04 §4.4](./04-interface.md))이
   클라이언트가 쥔 K 와 같다. `verify_owner` 가 `Ok(True)` → 200. §3.3 이 보였듯 만료 문구 401 의
   유일한 원인인 `EXPIRED` 는 TTL 초과에서만 나오므로 여기서 발생하지 않는다.
4. **`turns`·`slots`·토큰이 보존된다 (c).** 세 값 모두 `sessions`/`session_auth` 행의 컬럼이다
   ([04 §2.2](./04-interface.md)). 따라서 5번째 발화는 `turns = 4` 에서 이어지고 10턴 캡이
   재시작으로 리셋되지 않는다. 라우팅에 쓰이는 `slots`(위기/중독 트랙 판정)도 유지되므로 상담
   맥락이 끊기지 않는다.
5. **`history` 가 복원된다 (d).** `history` 는 스토어에 없다(P-경계). 대신 `restore_history`
   ([04 §1.5 #8](./04-interface.md))가 `turn_partitions` 가 지목한 날짜 파일만 열어 `(day, seq)`
   순으로 정렬하고, role 화이트리스트와 `context_excluded` 필터를 적용해 조립한다
   ([03 §5](./03-history-restore.md)). 대화 JSON 역시 같은 `/app/data` 볼륨에 있으므로 재기동을
   넘긴다.

**(d)가 (a)~(c)와 다른 매체에 의존한다는 점이 중요하다.** 세션 레코드만 영속하고 대화 JSON 이
휘발하면 "세션은 살았는데 모델이 앞 대화를 잊은" 부분 실패가 된다 — Phase 3 §1 이 대안 ③으로
평가하고 기각한 상태와 결과적으로 같다. 그래서 I3 의 전제는 "스토어가 영속"이 아니라
**"두 매체가 같은 영속 볼륨에 있다"**(전제 T2)이다.

#### 4.3 주장하지 않는 것 — 내구성의 한계를 정직하게

- **호스트 전원 상실·OS 크래시는 범위 밖이다.** [04 §7.2](./04-interface.md)가
  `PRAGMA synchronous = NORMAL` 을 확정했다. WAL + NORMAL 조합에서 커밋은 **애플리케이션
  프로세스의 죽음**에는 안전하지만(커밋 레코드가 이미 OS 페이지 캐시를 통해 WAL 에 들어갔다),
  **호스트 단위 전원 상실**에서는 최근 커밋 일부가 유실될 수 있다. 이 범위를 넓히려면
  `synchronous = FULL` 이 필요하고 대가는 커밋마다의 fsync 지연이다 — 이번 설계 범위 밖의
  결정이므로 여기서는 **범위를 좁혀 주장한다.**
- **볼륨이 실제로 마운트돼 있어야 한다.** D01 "대가와 한계"가 남긴 미확인 항목(배포 볼륨이
  블록 디바이스인지)이 정확히 여기 걸린다. 네트워크 파일시스템이면 SQLite 락 보장이 깨져
  I1·I3·I4 가 함께 무너진다.
- **`data/conversations/**` 의 보존기간 정책은 여전히 미해결이다.** `docs/security-review.md §5`
  (a)~(e)는 Phase 3 §6.2 가 기록한 대로 하나도 해소되지 않았다. 대화 파일이 어떤 정책으로든
  삭제되면 (d)만 실패하는 부분 실패가 생긴다.

### 반증 조건

1. 재기동 직후 같은 `session_id`·같은 토큰 요청이 401 을 받는다 → (b) 반증.
2. 재기동 직후 응답의 `turn` 값이 재기동 전보다 작다 → (c) 반증(카운터 리셋).
3. 재기동 직후 응답에 `session_token` 이 다시 실린다 → `created = True` 로 처리됐다는 뜻이며
   (a) 반증.
4. 실행 중 `sessions.db` 의 경로가 마운트된 볼륨 밖이다(`docker inspect` 의 Mounts 와 대조) →
   §4.1 의 (v2) 반례로 전락한다.
5. 컨테이너 재생성(이미지 교체) 후 `sessions` 테이블이 비어 있다.
6. `turns`·`slots` 는 보존되는데 `history` 만 빈다 → `data/conversations/**` 가 볼륨 밖이거나
   `turn_partitions` 가 비어 있다. (d)만의 부분 실패.
7. 재기동 후 스키마 초기화가 기존 행을 지운다(`DROP TABLE` 계열이 초기화 경로에 있다).
8. **호스트 전원 상실 후 마지막 몇 커밋이 사라진다** → 이것은 **반증이 아니라 §4.3 이 명시한
   범위 밖**이다. 반증으로 접수하면 안 된다. 다만 그 손실이 허용 불가라고 판단되면 그때
   `synchronous = FULL` 로의 변경이 별도 결정 대상이 된다.

## 5. I4 — 대화 쓰기 직렬화 정확성

### 주장

같은 세션에 대해 두 워커가 동시에 대화 턴을 기록해도 **턴이 유실되지 않는다.** 정확히는,
성공한 `append_conversation_turn` 호출 하나당 대화 JSON 에 턴이 정확히 하나 늘고, 그 좌표
`(day, seq)` 는 중복되지 않는다.

### 논증

#### 5.1 먼저 — 스토어 이전만으로는 아무것도 해결되지 않는다

CAP20 의 적대적 노트가 지목한 실패 모드가 "스토어로 옮겼으니 공짜로 해결됐다"고 적는 것이다.
그 서술이 왜 틀렸는지부터 확정한다.

`append_turn`(`app/storage.py:71-92`)이 쓰는 대상은 **세션 스토어가 아니라 디스크 JSON** 이다.

```
storage.py:88   raw ← path.read_text(...)          ← 읽기
storage.py:91   turns.append({"seq": len(turns), …}) ← 메모리에서 수정
storage.py:92   path.write_text(...)               ← 파일 전체 재작성
```

`_sessions` 를 SQLite 로 옮겨도 이 세 줄은 **한 글자도 달라지지 않는다.** 게다가 이 경로에는
오늘 **락이 아예 없다** — `threading.Lock` 은 `app/ratelimit.py:73` 에 있고 레이트리밋 상태
전용이며, `app/storage.py` 에는 어떤 동시성 프리미티브도 없다. 오늘 이 코드가 무사했던 이유는
락이 아니라 `--workers 1` 고정(`Dockerfile:30`)이다.

(부수 관측: `app/main.py:20` 의 `def post_chat(...)` 은 `async def` 가 아닌 **동기 함수**이므로
Starlette/FastAPI 는 이를 스레드풀에서 실행한다. 따라서 단일 워커에서도 같은 세션에 대한 동시
요청이 실제로 병렬 실행될 수 있다. 이 관측은 I4 의 논증에 필요하지 않지만, 블로커 3 이 다중
워커 이전에도 도달 가능함을 시사하므로 §9 에 발견사항으로 남긴다.)

#### 5.2 시나리오 W — 오늘의 턴 유실 (2 워커 동시 쓰기)

```
t0   data/conversations/2026-07-28/s1.json 의 turns 길이 = 4   (seq 0..3)

t1   워커 A: 요청 R1 정상 경로 → app/chat.py:498 → storage.append_turn(s1, "user", …)
        storage.py:88  읽기 → turns 길이 4
        storage.py:91  메모리에서 seq=4 로 append

t2   워커 B: 요청 R2(같은 세션) → app/chat.py:498 → storage.append_turn(s1, "user", …)
        storage.py:88  읽기 → A 가 아직 안 썼으므로 여전히 길이 4
        storage.py:91  메모리에서 seq=4 로 append        ← 같은 좌표

t3   워커 A: storage.py:92  write_text → 파일 5턴 (A 의 발화 포함)
t4   워커 B: storage.py:92  write_text → 파일 5턴 (B 의 발화 포함, A 의 발화 소멸)

결과  A 의 사용자 발화가 영구 유실. 이어지는 :499 의 assistant 턴까지 섞이면
      user/assistant 짝이 어긋난다.
```

**이 유실은 조용하다.** 결과 파일은 JSON 문법상 멀쩡하고 `seq` 도 `0..4` 로 연속이라
`normalize_conversation_payload`(`app/storage.py:39`)를 포함한 어떤 검증도 이상을 감지하지
못한다. 감사 기록이 소리 없이 틀려지는 것이 이 결함의 성질이다.

#### 5.3 Phase 4 §6.2 의 임계 구역이 이 시나리오를 어떻게 닫는가

같은 t0 에서 출발해 두 워커가 `append_conversation_turn` 을 호출한다.

```
워커 A                                     워커 B
BEGIN IMMEDIATE  ← 단일 writer 자리 획득
  1. 세션 레코드 조회 + TTL 판정             BEGIN IMMEDIATE  ← 대기
  2. 파일 read (turns 길이 4)                   (A 가 COMMIT 할 때까지 진입 불가.
  2'. 미커밋 꼬리 조정 (정상 경로에선 무동작)     busy_timeout 5초 초과 시 Err(CONFLICT))
  3. seq ← committed' = 4
     turn_partitions[day] ← 5
  4. tmp write → os.replace  (원자적 교체)
  5. COMMIT
                                            ─▶ 여기서부터 진입
                                              2. 파일 read → 길이 5 (A 의 턴 포함)
                                              3. seq ← committed' = 5   ← 겹치지 않는다
                                              4. os.replace → 6턴
                                              5. COMMIT
```

핵심은 네 가지이며, **넷 다 설계 선택이지 스토어 도입의 부산물이 아니다.**

1. **락이 트랜잭션 그 자체다.** [04 §6.1](./04-interface.md)이 별도 락 테이블을 두지 않고
   `BEGIN IMMEDIATE` 를 락으로 확정했다. 사유: 락 테이블은 실제 병렬성을 늘리지 못하면서(어차피
   writer 는 1개) **해제 누락**이라는 새 실패 모드를 만든다. 트랜잭션은 프로세스가 죽으면
   SQLite 가 자동 롤백한다.
2. **파일 I/O 가 락 안에 있다.** D05 의 확정("쓰기를 세션 스토어 트랜잭션/락으로 직렬화")이
   여기서 실체를 갖는다. 단계 2(read)와 단계 4(replace)가 락 밖에 있으면 §5.2 의 인터리빙이
   그대로 되살아난다 — 이것이 "스토어 이전만으로는 해결되지 않는다"의 정확한 이유다.
3. **`seq` 를 파일 길이가 아니라 인덱스의 커밋 개수에서 뽑는다.** [04 §6.2](./04-interface.md)
   단계 3 의 ★ 표시 지점이다. 이 선택이 없으면 §6.5 국면 ②의 A/B 시퀀스대로 고아 턴이 좌표
   계산에 끼어든다(→ I6 반증).
4. **파일 교체가 원자적이다.** 단계 4 는 tmp write + `os.replace` 다. 오늘
   `app/storage.py:92` 의 `write_text` 직접 쓰기와 달리 중간 상태가 없고, 같은 리포의
   `app/ratelimit.py:85-88` 이 이미 3-OS CI 로 검증한 관례를 따른다.

**결론**: `BEGIN IMMEDIATE` 가 단일 writer 자리를 트랜잭션 시작 시점에 잡으므로(P-직렬화),
두 임계 구역은 겹치지 않는다. B 의 단계 2 읽기는 항상 A 의 `os.replace` **이후**의 파일을 보고,
B 의 `seq` 는 A 의 커밋이 남긴 `turn_partitions[day]` 에서 나온다. 따라서 저장된 턴 수는 성공한
호출 수와 정확히 같고, 이 성질은 워커 수에 의존하지 않는다.

#### 5.4 임계 구역 길이의 상한 — 근거를 정정한다

[04 §6.3](./04-interface.md)은 임계 구역 길이의 상한을 "세션당 저장 턴 ≤ 20(요청 턴 10 ×
user/assistant)"에서 유도했다. **§6.5 가 택한 (B) 보존안 아래서 이 수치는 정확하지 않다.**

- (B)는 미커밋 꼬리를 파일에 **그대로 둔다**. 따라서 파일이 실제로 담는 턴 수는 `20 + F` 이며,
  `F` 는 COMMIT 실패로 남은 미커밋 append 수다.
- `F` 를 묶는 것은 `MAX_TURNS = 10`(`app/chat.py:15`)이 **아니다.** 실패한 append 는 `turns` 를
  증가시키지 않으므로 10턴 캡에 걸리지 않는다. `F` 를 실제로 묶는 것은 **D04 의 레이트리밋**
  (IP당 슬라이딩 윈도우 + 전역 일일 캡)이다 — 실패한 append 도 요청 하나를 소비하기 때문이다.

**결론은 바뀌지 않고 근거가 바뀐다.** 임계 구역 길이는 여전히 유한하고 세션 수·운영 일수와
무관하지만, 그 유한성의 출처는 "세션당 상수"가 아니라 **"요청률 상한"** 이다. 어떤 이행이
`F = 0` 을 가정하거나 파일 크기를 세션당 상수로 하드코딩하면 그 가정은 크래시가 반복되는
환경에서 깨진다. 같은 이유로 [04 §6.5](./04-interface.md)가 적은 "`context_excluded` 가
크래시당 최대 1~2 원소 커진다(세션당 저장 턴 ≤ 20 이라 상수로 묶인다)"도 근거를 `F` 로 바꿔
읽어야 한다.

### 반증 조건

1. 2워커 구성에서 같은 세션에 K 개의 요청을 동시에 넣은 뒤, 대화 파일의 턴 수가 성공 응답
   수에 대응하는 개수보다 **적다** → I4 직접 반증.
2. 한 날짜 파일 안에 같은 `seq` 를 가진 턴이 둘 이상 있다 → 좌표 유일성 반증.
3. 이행 완료 후 `grep -rn 'storage\.append_turn' app/` 이 비어 있지 않다 → 임계 구역을 우회하는
   두 번째 쓰기 경로가 남았다(오늘 9곳, [03 §5.2](./03-history-restore.md)).
4. 구현이 파일 교체(단계 4)를 쓰기 락 획득 **전에** 수행한다 → §5.3 의 2번 조건 위반.
5. 구현이 `BEGIN`(DEFERRED)로 시작해 단계 3 에서 쓰기로 승격한다 → [04 §4.3](./04-interface.md)이
   경고한 승격 교착·`SQLITE_BUSY` 빈발이 관측된다.
6. 워커마다 서로 다른 `data/sessions.db` 를 연다(I1 반증 3과 공유) → 두 임계 구역이 서로를
   배제하지 못한다.
7. 볼륨이 네트워크 파일시스템이다 → 파일락 보장이 깨진다(D01 한계).
8. `busy_timeout` 5초([04 §6.3](./04-interface.md))가 정상 부하에서 상시 도달한다 → 임계 구역이
   설계 상한을 넘었다는 신호이며, 금지 항목(LLM 호출·네트워크 I/O·디렉터리 전수 스캔)이 임계
   구역에 들어왔는지 점검해야 한다.

## 6. I5 — 인증·캡의 워커 횡단 정확성

### 주장

- **(A) CAP15**: 클라이언트에게 발급된 `session_token` 은 항상 스토어에 **실재하는 행**의
  값이며, 따라서 어느 워커에서 검증해도 같은 판정이 난다. "내가 가진 토큰을 어떤 워커도 모른다"는
  상태가 **표현 불가능**해진다.
- **(B) CAP14**: 어떤 워커 수에서도 `sessions.turns ≤ max_turns` 이고, `limit_reached = False`
  로 끝나는 `consume_turn` 성공은 세션당 **정확히 `max_turns` 회**다. 캡은 워커마다가 아니라
  세션당 한 번 성립한다.

### 논증 (A) — Phase 4 가 실제로 고른 생성 시맨틱 위에서

#### 6.1 오늘 열려 있는 창

```
app/main.py:43   session_was_known = chat.has_session(session_id)     ← 왕복 1 (읽기)
app/main.py:57   result = chat.handle_message(...)                    ← 왕복 2 (내부 _get_session 이 생성)
app/main.py:59   result["session_token"] = chat.session_token(...)    ← 왕복 3 (읽기)
```

두 워커가 같은 `session_id` 로 동시에 첫 요청을 받으면, 둘 다 왕복 1 에서 `False` 를 보고 각자
`_get_session`(`app/chat.py:78-83`)으로 **서로 다른** `ChatSession` 을 자기 프로세스 dict 에
만든다. 토큰은 `app/chat.py:49` 의 `secrets.token_urlsafe(32)` 기본 팩토리라 두 값이 다르다.
이후 요청이 반대 워커로 가면 `owns_session`(`app/chat.py:64-70`)의
`secrets.compare_digest`(`:69`)가 실패해 `app/main.py:46` 의 401 이 **영구히** 반복된다 —
새 세션으로 시작하지 않는 한 회복 경로가 없다.

#### 6.2 채택된 시맨틱과 그것이 만드는 성질

[04 §4.2](./04-interface.md)는 세 후보 중 **"단일 트랜잭션 내 조회-생성 통합"** 을 택했다.
나머지 둘이 왜 부족한지가 논증의 절반이다.

| 후보 | 판정 | 사유 |
|------|------|------|
| 덮어쓰기(`INSERT OR REPLACE`) | 기각 | 나중 워커가 앞 행을 덮어써 앞 클라이언트의 토큰이 그 순간 무효가 된다 — 메모리 dict 시절의 영구 401 을 스토어 안으로 옮기는 셈. 게다가 쌓인 `turns`/`slots` 가 소실된다 |
| `INSERT OR IGNORE` 단독 | 불충분 | 원자성은 얻지만, 호출부가 *방금 만든* 토큰을 그대로 반환하면 `INSERT` 가 무시된 경우 **패자의 토큰**이 나간다. 원자적인데도 영구 401 이 남는다 |
| **단일 트랜잭션 내 조회-생성 통합 (채택)** | 채택 | `BEGIN IMMEDIATE` 안에서 조회·만료정리·생성·**재조회**를 모두 수행하고 그 결과를 반환한다 |

채택안의 결정적 부분은 **COMMIT 직전 재조회**([04 §4.3](./04-interface.md)의 ★)다.

> **성질 P1 (승자 토큰).** `open_session` 이 반환하는 `SessionView.session_token` 은 항상 그
> 시점 `session_auth` 테이블에 **실재하는 행**의 값이다.

논증: 토큰은 재조회의 `SELECT` 결과에서만 나온다. 그 `SELECT` 는 같은 트랜잭션 안에서
실행되므로 다른 워커의 개입이 불가능하고, 반환된 행은 정의상 테이블에 있다. 따라서 **테이블에
없는 행의 토큰이 클라이언트에게 나가는 경로가 존재하지 않는다.** §6.1 의 영구 401 은 "고쳐진"
것이 아니라 **발생 가능한 상태 자체가 사라진다.**

여기에 매체 하나(P-매체)가 더해져 CAP15 의 진술이 완성된다: `verify_owner`
([04 §1.5 #3](./04-interface.md))는 어느 워커에서든 같은 `session_auth` 행을 읽어
`secrets.compare_digest`(`app/chat.py:69` 의 상수시간 비교 유지)로 판정하므로, 워커 A 가 발급한
토큰이 워커 B 에서 통한다.

**가장 좁은 목**: 생성이 `sessions` 와 `session_auth` **두 테이블**에 걸친다
([04 §7.4](./04-interface.md)의 인증 필드 고립). 두 `INSERT` 가 반드시 같은 트랜잭션 안에
있어야 하며, 한쪽만 커밋되면 "행은 있는데 토큰이 없는 세션"이 생겨 P1 이 즉시 깨진다.

#### 6.3 P1 이 주장하지 않는 것 — 대가를 정직하게

P1 은 "동시 첫 요청을 보낸 두 클라이언트가 **같은 토큰을 받는다**"는 뜻이 **아니다.**
[04 §4.4](./04-interface.md)의 토큰 응답 규정은 `created = True` 일 때만 토큰을 동봉하고,
`created = False` + 토큰 없음/불일치는 401 `"세션 인증이 필요합니다."` 다. 따라서 같은
클라이언트가 첫 요청을 **중복 전송**해 두 워커에 동시에 닿으면 **진 쪽은 401 을 받는다.**
오늘(단일 워커, 왕복 1 의 stale read)은 양쪽이 같은 토큰을 받으므로 이것은 **동작 변화**다.

Phase 4 가 이 대가를 택한 사유를 그대로 유지한다: 오늘의 그 동작은 동시에 **토큰 유출 경합**
이기도 하다. `session_id` 는 클라이언트가 정하는 값이므로(`app/main.py:21`) 추측·열거가
가능한데, 공격자가 토큰 없는 요청을 정확히 생성 순간에 끼워 넣으면 왕복 1 에서 `False` 를 얻어
왕복 3 에서 **피해자 세션의 토큰**을 받는다. 새 규정은 그 창을 닫는다. 중복 전송의 대가는
401 이라는 **소리 나는 실패**(클라이언트가 새 세션으로 복구 가능)인 반면, 유출은 조용하다.

정리하면 CAP15 의 진술은 **"발급된 토큰에 대해"** 성립한다 — 발급되지 않은 요청은 401 을 받고
그것은 설계된 동작이다.

### 논증 (B) — 10턴 캡

#### 6.4 오늘의 check-then-act 창

`session.turns` 는 세 곳에서 증가하고(`app/chat.py:325`, `:408`, `:503`) 세 곳에서 판정된다
(`:328`, `:358`, `:505`). 문제는 판정과 증가의 **거리**다 — 진입부 `:358` 에서
`session.turns >= MAX_TURNS` 를 확인하고, 증가는 LLM 호출(`:462-468`)을 지나 `:503` 에서
일어난다. 창의 길이가 네트워크 왕복만큼이다.

그리고 오늘은 그 이전에 더 근본적인 문제가 있다: dict 가 프로세스별이라 **캡 자체가 워커마다
따로 논다.** `Dockerfile:28-29` 가 `--workers 1` 고정 사유로 정확히 이 문장을 적고 있다.

#### 6.5 채택안 — 판정을 `WHERE` 절로 내린다

[04 §5.2](./04-interface.md)의 `consume_turn` 은 판정과 증가를 **한 `UPDATE`** 로 묶는다(R2).

```
BEGIN IMMEDIATE
  UPDATE sessions
     SET turns = turns + 1, last_activity_at = <now>
   WHERE session_id = ? AND turns < <max_turns>      ← 판정이 WHERE 절
  영향 행 수 == 0  →  limit_reached = True           ← 캡 도달
  영향 행 수 == 1  →  turn_no = 갱신된 turns
COMMIT
```

두 워커가 동시에 `turns == 9` 에서 출발해도, `BEGIN IMMEDIATE` 가 직렬화하므로(P-직렬화) 조건
`turns < 10` 을 만족시키는 쪽은 **하나뿐**이다. 진 쪽은 영향 행 수 0 을 받아
`limit_reached = True` 로 `LIMIT_MESSAGE`(`app/chat.py:17`) 경로를 탄다.

따라서 (i) 어떤 인터리빙에서도 `turns ≤ max_turns` 이고, (ii) 성공 소비 횟수가 세션당 정확히
`max_turns` 다. **워커마다가 아니라 세션당 한 번**인 이유는 단순하다 — 캡의 상태가 곧 행 하나의
컬럼이고, 그 행이 하나뿐이기 때문이다.

`max_turns` 는 스토어의 상수가 아니라 **인자**다([04 §1.5](./04-interface.md) 비고). 정책 상수
`MAX_TURNS = 10` 은 `app/chat.py:15` 에 남는다. 캡의 **값**은 정책이 정하고 캡의 **원자성**만
스토어가 제공한다.

#### 6.6 "카운터가 정확하다"만으로는 CAP14 가 충족되지 않는다

[04 §5.3](./04-interface.md)이 기각한 대안 — 판정은 진입부에서 낙관적으로 하고 증가만 말미에
원자적으로 하는 안 — 을 반례로 확인해 둔다. 두 워커가 동시에 `turns == 9` 를 통과하면
**응답 두 개가 생성된 뒤** 증가 하나만 성공한다. `turns` 는 10 을 넘지 않지만 **11번째 응답이
이미 사용자에게 나갔다.** 캡의 목적이 응답 수 제한이므로 이 잔여는 캡을 실질적으로 무력화한다.
그래서 I5-(B)의 주장은 "카운터 값"이 아니라 **"성공 소비 횟수"** 로 진술돼 있다.

보상 연산 `release_turn`([04 §5.3](./04-interface.md))의 가드 `WHERE turns = <turn_no>` 도 같은
논리의 일부다 — 그 사이 다른 워커가 이미 전진했다면 되돌림은 무동작(`Ok(False)`)이 되어, 되돌림이
남의 소비를 지우지 않는다. 잔여 손실(턴 1개)은 스스로 한정된다.

### 반증 조건

1. 어느 시점에든 `SELECT turns FROM sessions WHERE session_id = ?` 가 `max_turns` 를 넘는다 →
   (B) 직접 반증.
2. 한 세션이 `limit_reached = False` 응답을 11개 이상 받는다 → **카운터가 10 이하여도 반증이다**
   (§6.6 의 잔여가 살아있다는 뜻).
3. 클라이언트가 200 응답으로 받은 토큰을 그대로 제시했는데 다음 요청에서 401 `"세션 인증이
   필요합니다."` 를 받는다 → P1 반증.
4. `sessions` 에 행이 있는데 대응하는 `session_auth` 행이 없다 → [04 §7.4](./04-interface.md)의
   두 `INSERT` 가 서로 다른 트랜잭션에 있다.
5. 이행 후 `consume_turn` **호출 전에** `SessionView.turns` 를 읽어 캡을 판정하는 코드가 남아
   있다(R2 위반) → check-then-act 창 부활. grep 으로 관측 가능.
6. `release_turn` 이 `WHERE turns = <turn_no>` 가드 없이 감소를 수행한다 → 다른 워커의 소비를
   되돌려 캡이 느슨해진다.
7. 워커별로 서로 다른 DB 파일을 연다 → 같은 세션에 `turns` 컬럼이 둘 생긴다(I1 반증과 공유).
8. `open_session` 이 재조회 없이 방금 생성한 토큰을 반환한다 → `INSERT` 가 무시된 경우 패자의
   토큰이 나가 P1 이 깨진다.

## 7. I6 — 복원 history 의 안전 경계

### 주장 (범위를 정확히 좁혀서)

> 애플리케이션 경로를 통해 기록되었고 그 시점 `safety.assess_prompt_injection`
> (`app/safety.py:207`)이 **차단한** 사용자 발화는, 복원된 `history` 에 **들어갈 수 없다.**

**주장하지 않는 것**: 대화 파일에 애플리케이션 경로를 거치지 않고 직접 쓰인 내용의 안전성.
그것은 이 설계가 새로 만드는 **부수 경계**이며 §7.3 에 별도로 기록한다. 두 가지를 뭉뚱그리면
방어 대상이 잘못 잡힌다.

### 논증

#### 7.1 여섯 단계

**(1) 경계의 술어.** [03 §2.2](./03-history-restore.md)가 실측으로 좁힌 등가성을 재확인했다.

> `user` 턴이 `history` 에서 제외됨 ⟺ 그 요청에서 `safety.assess_prompt_injection(message).blocked`
> 가 참이었음

차단 분기는 `app/chat.py:373` 이다. 그 안에서 중독 라우트가 감지되면 `:391` 이
`_handle_addiction_route(..., include_user_in_model_context=False)` 로 **조기 return** 하고
(정의 `app/chat.py:283`, 기본값 `:290` `include_user_in_model_context: bool = True`), 정상 경로의
호출부 `:427` 은 기본값 `True` 를 쓴다. 차단 분기의 나머지 갈래는 `:405` 에서 `user` 를 저장하고
`:407` 에서 `assistant` 만 `history` 에 넣는다. 즉 **`user` 발화가 history 에서 빠지는 것은 차단
분기 안에서만** 일어난다.

**(2) 판정이 쓰기 시점에 기록된다.** [04 §6.2](./04-interface.md)의
`append_conversation_turn(..., exclude_from_context, now)` 이 호출 지점별로 값을 확정한다 —
`app/chat.py:405` 는 `True` 고정, `:320` 은 `not include_user_in_model_context`, `:498` 은
`False`. 인덱스 갱신(단계 3)은 파일 교체(단계 4)·`COMMIT`(단계 5)과 **같은 트랜잭션**이다.

**(3) 키를 호출부가 추정하지 않는다.** [03 §5.2](./03-history-restore.md)가 호출부의
`date.today()`/`len(turns)` 재계산을 **금지**했고(자정 경합·off-by-one), [04 §6.2](./04-interface.md)는
한 걸음 더 나아가 인덱스 갱신을 **스토어가 직접** 수행한다 — 정합성이 호출부의 행동에 의존하지
않는다. 게다가 `now` 는 인자이므로(P-시간) 한 요청 안에서 시간 기준이 두 번 평가되지 않는다.

**(4) 꼬리 폐쇄성.** [04 §6.5](./04-interface.md)의 불변식이다.

> 어느 시점에 복원하더라도, `context_excluded` 에 등재되지 않은 채 수용 범위
> (`seq < turn_partitions[day]`) 안에 있는 턴은 존재하지 않는다.

논증 골자: 턴이 수용 범위로 들어오는 경로는 둘뿐이다 — (i) **자기 append 의 커밋**(그 커밋이
`exclude_from_context` 판정을 같은 트랜잭션에서 함께 쓴다), (ii) **다음 append 의 조정**
([04 §6.2](./04-interface.md) 단계 2'; 그 조정이 등재를 같은 트랜잭션에서 함께 쓴다). 두 경로
모두 "수용 범위 진입"과 "등재 여부 확정"이 **하나의 커밋 경계** 안에 있으므로, 등재 없이 수용된
상태는 만들어지지 않는다. 조정은 등재 여부를 **알 수 없는** 고아를 전부 제외로 확정한다
(fail-closed) — 이 방향이 안전한 쪽이다.

**(5) 읽기 측 두 필터.** 복원은 `key ∈ context_excluded` 인 턴을 버리고
([03 §5](./03-history-restore.md) 5단계), `seq ≥ turn_partitions[day]` 인 꼬리를 잘라낸다
([04 §6.5](./04-interface.md) 국면 ①). 여기에 role 화이트리스트(`user`/`assistant` 만 통과,
[03 §4](./03-history-restore.md))가 더해져 `intake_summary` 는 애초에 후보가 아니다.

**(6) 결론.** 차단된 `user` 턴이 있을 수 있는 상태는 둘뿐이다 — (a) 수용 범위 안이면 (4)에 의해
반드시 `context_excluded` 에 등재돼 있으므로 5단계에서 탈락한다, (b) 수용 범위 밖이면 국면 ①에서
잘린다. **제3의 상태를 (4)가 배제한다.** 그리고 복원은 스토어 레코드가 있을 때만 돌므로
([03 §5.1](./03-history-restore.md)) "인덱스 없는 복원"이라는 경로도 없다.

**이 논증이 의존하지 않는 것**: `assess_prompt_injection` 이 앞으로도 같은 답을 준다는 것.
Phase 3 이 해소안 (나)(복원 시 재판정)를 버린 이유가 정확히 이것이다 — 판정은 **기록**이지
재계산이 아니므로 판정기 개정에 면역이다.

#### 7.2 완전성의 한 구멍 — 안전 방향은 무사하다

[04 §6.4](./04-interface.md) 5행(COMMIT 실패/크래시)이 남긴 고아는 **다음 append 가 같은 날짜에
올 때** 단계 2' 의 조정으로 등재된다. 그런데 조정이 보는 것은 `now.date` 파티션 **하나뿐**이다
([04 §6.2](./04-interface.md) 단계 2). 그래서 다음이 성립한다.

```
크래시가 어떤 날짜 D 의 첫 append 에서 났다:
    파일 data/conversations/D/{sid}.json  = 1턴
    turn_partitions 에 D 키 없음 (인덱스 롤백)

다음 append 가 D 가 아니라 D+2 에 떨어지면:
    D+2 의 조정은 D 를 보지 않는다  →  D 는 turn_partitions 에 영영 들어가지 않는다
    복원은 turn_partitions 의 키만 연다  →  D 의 턴은 영구히 보이지 않는다
```

- **안전 방향(I6 의 주장)은 무사하다.** 보이지 않는다는 것은 모델 컨텍스트에 들어갈 수 없다는
  뜻이고, 감사 기록(대화 JSON)에는 그 턴이 그대로 남는다 — fail-closed 다.
- **충실도 방향은 다르다.** [03 §5.3](./03-history-restore.md)의 **`turn_days` 완전성** 불변식
  ("이 세션의 턴이 존재하는 모든 날짜 파티션이 `turn_days` 에 있다")은 이 시나리오에서 **거짓**
  이 된다. [04 §6.4](./04-interface.md) 5행의 "충실도만 손실"은 "다음 append 까지의 일시적 손실"로
  읽히기 쉬우나, 이 경우 손실은 **영구적이고 범위가 그 날짜 파티션 전체**다.
- **판정**: I6 의 주장(안전)은 무조건 성립한다. **완전성 불변식은 조건부로만 성립한다** —
  "고아가 생긴 날짜에 이후 append 가 최소 1회 더 있다"는 조건 아래서다. 이 조건을 밝히지 않은 채
  완전성을 무조건 주장해서는 안 된다. 해소는 이행 설계에서 가능하다(예: 조정 대상을 `now.date`
  뿐 아니라 마지막 활동 이후 파티션까지 넓히거나, 세션 재개 시 1회 점검). 이 문서는 조건을
  **드러내는 데까지**만 하고 해소는 Phase 6 에 넘긴다(§9).

#### 7.3 부수 경계 — 디스크 경유 조립이 만드는 새 주입 경로

**오늘은 존재하지 않는 경계다.** 오늘 `session.history` 는 프로세스 메모리 리스트이고, 값이
들어가는 곳은 5곳뿐이다(`app/chat.py:323`, `:324`, `:407`, `:501`, `:502`). 그 값의 출처는
**이번 요청의 메시지**와 **모델 응답**뿐이다 — 디스크의 어떤 내용도 모델 컨텍스트에 닿지 않는다.

복원을 도입하면 그 성질이 사라진다. `restore_history` 는
`data/conversations/{day}/{sid}.json` 의 `text` 를 읽어 `content` 로 사상하고

| 볼륨 접근 주체(운영자, 컨테이너 내 다른 프로세스, 백업 복원) | `/app/data`(`Dockerfile:21`)에 직접 파일 쓰기 | **쓰기 주체. 코드 경로가 없다** — 어떤 애플리케이션 검증도 거치지 않는다 |
| `scripts/load_to_sqlite.py` | `:145-146` 이 대화 파일을 **읽어** `:162` 이후 `chatlog.db` 에 적재한다 | **쓰기 주체가 아니라 소비자.** 오염된 파일이 분석 DB·`GET /api/stats` 로 전파되는 **2차 경로** |

> **정정**: 배치 적재는 주입 **주체**가 아니라 **전파 경로**다. 이 구분을 흐리면 방어 대상이
> 잘못 잡힌다 — `load_to_sqlite.py` 를 막아도 주입은 막히지 않고, 대화 파일 쓰기를 막으면 둘 다
> 막힌다.

**`_SAFE_ID_RE` 는 이 경계를 막지 못한다.** `app/storage.py:16`
`_SAFE_ID_RE = re.compile(r"[A-Za-z0-9._-]{1,128}")` 는 `valid_session_id`(`:19-21`)와
`valid_participant_id`(`:24-26`)를 통해 **파일명**만 제약한다. 목적은 경로 순회 차단이고,
`turns[].text` 의 **내용**에는 어떤 제약도 없다. "id 화이트리스트가 있으니 안전하다"는 추론은
성립하지 않는다.

**설계가 실제로 좁혀 주는 범위 (과장 없이).**

| 공격 형태 | 막히는가 | 근거 |
|-----------|----------|------|
| 임의의 `{sid}.json` 을 심어 둔다 | **막힌다** | 스토어 레코드가 없으면 복원이 아예 돌지 않는다([03 §5.1](./03-history-restore.md)) |
| 과거 날짜 디렉터리에 파일을 심는다 | **막힌다** | `turn_partitions` 에 없는 날짜는 열리지 않는다([03 §3.3](./03-history-restore.md)) |
| 기존 파일 **뒤에 이어 붙인다** | **막힌다** | 수용 범위 밖 꼬리는 국면 ①에서 잘린다([04 §6.5](./04-interface.md)) |
| **이미 수용된 턴의 `text` 를 제자리에서 바꾼다** | **막히지 않는다** | 턴 **수**가 그대로라 국면 ①의 개수 검사를 통과하고, `context_excluded` 에도 없으므로 5단계 필터도 통과한다. 설계에 내용 무결성 검증(해시·MAC)이 없다 |

마지막 행이 이 경계의 실체다. 그리고 볼륨에 쓸 수 있는 주체는 `data/sessions.db` 에도 쓸 수
있으므로 인덱스까지 고칠 수 있다 — 즉 **볼륨 쓰기 권한은 곧 모델 컨텍스트 쓰기 권한**이다.

**이것을 결함이 아니라 신뢰 경계의 이동으로 기록한다.** 오늘 `data/` 는 "기록되는 곳"이었고,
복원 도입 이후에는 **"모델에게 읽히는 곳"** 이 된다. 그 결과 `docs/security-review.md §5` (d)
(파일 권한 최소화)의 성격이 바뀐다 — 지금까지 **기밀성** 항목이었던 것이 복원 이후에는
**무결성** 항목이 되고, 위험 등급이 올라간다. 이 승격의 실제 해소는 이번 task 범위 밖(공개
전환 전 보안·법무 검토)이지만, 그 검토의 **입력**으로 여기 남긴다.

### 반증 조건

1. 복원 결과에 `(day, seq) ∈ context_excluded` 인 턴이 하나라도 있다 → 5단계 필터 반증.
2. 복원 결과에 `seq ≥ turn_partitions[day]` 인 턴이 있다 → 국면 ① 미적용.
3. 구현이 `seq` 를 `len(payload["turns"])`(파일 길이)에서 뽑는다 →
   [04 §6.5](./04-interface.md) 국면 ②의 A/B 시퀀스로 고아 부활이 **재현 가능**하다.
4. 호출부에 `date.today()`/`len(turns)` 로 키를 재계산하는 코드가 남아 있다 →
   [03 §5.2](./03-history-restore.md) 금지 규정 위반. grep 으로 관측 가능.
5. 스토어 레코드 없이 복원이 도는 경로가 생긴다 → [03 §5.1](./03-history-restore.md) 위반이자
   §7.3 의 첫 번째 방어선 상실.
6. role 필터가 화이트리스트가 아니라 블랙리스트(`role != "intake_summary"`)로 구현된다 →
   장래의 새 저장 전용 role 이 컨텍스트로 들어간다.
7. 차단 판정이 참인데 `exclude_from_context` 가 `False` 로 전달되는 호출 지점이 있다 →
   [04 §6.2](./04-interface.md) 확정표와 실제 호출부를 대조해 관측한다.
8. **§7.2 한정 조건의 반증**: 고아가 남은 날짜에 이후 append 가 없는 세션에서 **그 날짜의 턴이
   복원에 나타난다** → §7.2 의 서술이 틀렸다. (나타나지 않으면 안전 방향이 확인되고 충실도
   손실이 확정된다 — 그 경우 반증이 아니라 §7.2 의 조건이 실측으로 확인된 것이다.)
9. **§7.3 좁힘 범위의 반증**: 스토어 레코드 없는 `{sid}.json` 을 심었는데 그 내용이 모델
   컨텍스트에 나타난다 → 레코드/파티션/개수 세 관문 중 하나가 실제로는 작동하지 않는다.

## 8. 종합 판정

### 8.1 목표 대비 판정

origin 의 최상위 목표 **"세션 상태를 프로세스 메모리에서 분리해 다중 워커와 서버 재시작을
견디게 만든다"** 는 **설계 수준에서 달성된다.** 근거는 다음 대응이다.

| origin 이 요구한 것 | 이 문서의 논증 | 대응 CAP |
|---------------------|----------------|----------|
| 요청이 어느 워커로 가도 같은 세션 상태를 본다 | I1 (§2) | CAP01 |
| 다른 워커로 갈 때마다 401 로 끊기지 않는다 | I2 (§3) | CAP12 |
| 재시작 후 진행 중 사용자가 막히지 않는다 | I3 (§4) + I2 (§3.3) | CAP02·CAP13 |
| `append_turn` 동시 쓰기로 턴이 유실되지 않는다 | I4 (§5) | CAP20 |
| 10턴 캡이 워커마다 따로 놀지 않는다 | I5-(B) (§6.4~6.6) | CAP14 |
| `owns_session` 인증이 워커를 넘어 성립한다 | I5-(A) (§6.1~6.3) | CAP15 |
| 복원이 안전 경계를 훼손하지 않는다 | I6 (§7) | CAP29 계열 |

### 8.2 판정에 붙는 다섯 전제

**"조건 없이 달성된다"고 쓰지 않는다.** 아래 다섯이 이행 단계에서 유지되어야 위 결론이 유지된다.

| ID | 전제 | 깨지면 무엇이 거짓이 되나 | 책임 |
|----|------|---------------------------|------|
| **T1** | 단일 호스트 멀티프로세스 범위. 멀티 인스턴스·NFS 아님 | I1·I4 (파일락·단일 writer 전제) | D01 이 확정. 배포 형상 확인은 Phase 7 |
| **T2** | `data/sessions.db` 와 `data/conversations/**` 가 **같은 영속 볼륨**에 있고 실제로 마운트된다 | I3 전부, I3-(d) 부분 실패 포함 | 배포 구성 |
| **T3** | `_sessions` 직접 접근 **37곳/13파일**과 `storage.append_turn` 호출 **9곳**이 전부 스토어 연산으로 이행된다 | I1·I4 가 **국소적으로** 거짓이 된다 — 남은 경로에서만 옛 결함이 살아난다 | **Phase 6** |
| **T4** | 모든 갱신이 `BEGIN IMMEDIATE` 단일 트랜잭션 안에 있고 R1(전체 덮어쓰기 API 금지)·R2(판정을 `WHERE` 로) 가 지켜진다 | I1(쓰기 경로)·I4·I5-(B) | **Phase 6** |
| **T5** | 내구성 주장의 범위는 프로세스 재시작이며, `synchronous = NORMAL` 아래서 호스트 전원 상실은 제외된다 | I3 의 범위 선언 — 넓히려면 별도 결정 | 이 문서가 범위를 명시 |

T3 이 가장 넓고 가장 잘 잊히는 전제다. **부분 이행은 부분 달성이 아니라 "어떤 요청 경로에서는
옛 결함이 그대로 살아있는 상태"** 이며, 그 상태는 재현이 간헐적이라 진단이 특히 어렵다.

### 8.3 `--workers 1` 해제와의 관계

`Dockerfile:30` 의 `--workers 1` 고정은 두 사유(`:25-29`)를 갖는다 — `RateLimiter` 의 프로세스
내부 락과 `_sessions` 프로세스 메모리 dict. 이 문서의 I1·I4·I5 가 후자를, D04 와
[04 §7.3](./04-interface.md)이 전자를 각각 닫는다. **해제 조건의 확정(CAP21)은 Phase 7 소관**
이지만, 이 문서 기준으로 그 필요조건은 **T3 의 완결**이다 — 하나라도 남으면 워커를 늘리는 순간
그 경로에서 옛 동작이 재현된다.
